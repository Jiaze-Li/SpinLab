# SpinLab 执行包

这里是给 Agent 派任务时直接用的材料。旧的设计文档（D6-A、D6-B、G0、新数据库 v0.2）保留作参考，不再作为派任务的输入；两边说法不一致时以这里为准。

## 里面有什么

- [`SKELETON.md`](SKELETON.md)：数据骨架。一页，每次派任务都附上。
- `brief-N-*.md`：每个任务一份需求。写的是"我要什么、不要什么、怎么验收"，以及 Agent 需要知道的代码现状。

## 任务顺序

| 顺序 | 任务 | 需求 | 流程 | 前置 |
|---|---|---|---|---|
| 1 | 新建样品，编号永久不变 | [`brief-1`](brief-1-create-sample.md) | 直接实现 | 无 |
| 2 | Registry 少一行不再删样品，删除暂时关闭 | [`brief-2`](brief-2-safety-guard.md) | 直接实现 | 任务 1 已合并 |
| 3 | 同一个 Library 只允许一个 SpinLab 可写 | [`brief-3`](brief-3-single-writer.md) | 直接实现 | 无 |
| 4 | 手填参数，确认后直接覆盖 | [`brief-4`](brief-4-parameters.md) | 直接实现 | 任务 1 已合并 |
| 5 | AFM 文件入库成标准数据（引入链接表） | D6-B 的 T03 任务卡，去掉"开工门槛" | 先设计 | 任务 1 |
| 6 | AFM 处理与出图改读标准数据 | D6-B 的 T04 任务卡，同上 | 先设计 | 任务 5 |
| 7 | AFM 自动出图 | D6-B 的 T05 任务卡，同上 | 先设计 | 任务 6 |

**进度不记在这里。** 哪个任务做完了、下一个是什么，看 [`docs/V5_ROADMAP.md`](../../../V5_ROADMAP.md) 的 5.6.x 段，用的是仓库原有的勾选方式（`[ ]` 未开始、`[~]` 进行中、`[x]` 已完成）。任务合并时在同一个 PR 里勾选。

任务 5 之后的需求在轮到它之前再写，写法照 `brief-1` 到 `brief-4`，写好后把表里的"需求"一栏改成指向新文件。

**任务 5 的必验项：** 同一 Dataset 若只是更正忠实解析或有证据的单位/角色解释，保留 datasetID；改变独立信号则新建。测试「旧更正 A 开始处理 → 新更正 B 先提交 → A 后完成」：A 必须因当前标记已变化而被拒绝，B 仍是当前内容，不能只凭主线程同步写入就省略校验。相同操作重试不得再次更新；成功更正须使受影响的 Result/Plot 过期，已保存的 Snapshot 不受影响。此条约束首次 Dataset 消费者的提交结果与验收，任务 5 设计时再选最小实现，不要求给任务 1–4 加机制。

**任务 6（首个 Live Result/Plot 消费者）的必验项：** 后台计算 A 读取输入/定义标记 v1 并完成初步校验；随后 Parameter 或 Dataset 更新 B 先提交并使相关 Live 过期；A 再尝试发布时，必须在不可交错的提交点重新核对全部直接/间接依赖和 Live 自身标记，拒绝旧输出，不能重新标为 `current`。反向顺序 A 先发布、B 后更新时，B 必须使该输出过期；输入值 A→B→A 也不得绕过单调标记检查。首次 Snapshot 消费者须同样测试「保存准备完毕、正式提交前依赖或归属被修改」，不得宣布 `saved` 或固定错误内容，已成功保存的快照在之后变更时保持不变。这些要求在对应任务的设计与验收中落地；不为任务 1–5 新建事务框架。

任务 3 没有前置，建议最先做。`SKELETON.md` 里"同一时间只有一个 SpinLab 可写"在它合并之前靠的是使用习惯（只开一个 App），合并之后才由程序保证。任务 1、2、4 不依赖它，是因为它们的写入都由主线程同步发起，单个 App 内不会互相打断。

任务 2 排在任务 1 之后，是因为它的代码（PR #195）叠在任务 1 的分支上，直接搬到 `main` 会冲突。在任务 2 合并之前，同步 Registry 前先看预览里 removed 的数量，不是 0 就不要点应用。

## 原来的 G0–G5 去哪了

不再作为单独的关卡。每块基础由第一个需要它的任务带着做：

| 原关卡 | 现在 |
|---|---|
| G0 设计准备 | 由 `SKELETON.md` 和各任务的 design 模式替代 |
| G1 数据安全 | 任务 2、任务 3 |

| G5 结果与自动执行 | 任务 6、任务 7 |

## 每个任务怎么走

对 Agent 说一句话就够：**"做 `docs/V5_ROADMAP.md` 5.6.x 段里下一个没打勾的任务。"** 它会找到对应的 brief，brief 末尾的"开工"一节写了分支、PR 和步骤。

**任务 1–4：直接实现。** 做法已经写在 brief 的"已定的做法"里，brief 本身就是合同，不需要单独的设计阶段。

**任务 5–7：先设计。** 这几个任务第一次引入 SQLite、链接表和标准数据的文件格式，定了就很难改，而且具体做法取决于任务 1–4 落地后的代码。轮到时：

1. 让 Agent 照 `brief-1` 到 `brief-4` 的格式起草该任务的 brief，你读过、改过。
2. Agent 以 `taskType: "design"` 调用 `reviewloop_begin`，brief 全文作为 `contractText`。通过后你会收到最多五行的摘要和一份"假设"清单，逐条读；有一条不符合你的实际情况就打回。
3. 确认后再开始实现。

## 三条止损规则

- 合同超过两页，说明任务太大。停下来拆任务，不要继续加内容。
- design 审查三轮没过，停下来。缩小需求再来，不要补更多机制。
- 合同里出现 brief 和 `SKELETON.md` 都没提到的机制（锁、日志、重试、新的状态），要求 Agent 说明是哪条需求需要它；说不出来就删掉。

## 你要做的只有三件事

1. 派任务前读一遍 brief，不符合你想法的地方先改 brief。
2. 合并前按 brief 里的"我怎么验收"亲手走一遍。
3. 任务 5 起，设计通过后读假设清单。
