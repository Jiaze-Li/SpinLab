# SpinLab — 收敛计划（2026-11-11）

**性质：** 对本目录冻结材料的一次只读审核结论，加上用户当天确认的三项决定和建议的后续顺序。它不是新的上位合同，不授权合并任何 PR、修改真实 Library 或迁移数据；每一步实施仍需用户单独同意。
**审核范围：** D6-A v1.3、D6-B v1.4、G0 v1.4、新数据库 v0.2、G1-01 冻结 Worker v1.0、G1-01 补充设计 v0.4，以及 `main`（`53c6dc6`）、PR #194（`d29d914`）、PR #195（`01e19d8`）的代码。未运行测试，未访问真实 Library。

## 1. 为什么推不动

产品架构本身（Sample 中心、接入 → 数据核心 → 分析 → 展示的分层）没有发现需要推翻的问题。停滞来自三处：

1. **功能排在三道基础关卡之后。** 路线图要求 G0 → G1 → G2 全部通过才能做 T01，每道关卡都要独立设计审查，而审查没有收敛条件：每一轮都能在上一轮新增的协议里找到新问题。
2. **G1 补充设计在防一个不存在的场景。** 它起于 PR #195 上一条 P2 评审意见（删除抽屉时用旧索引覆盖"并发写入者"的更新），随后长成跨进程锁、Root 身份登记、操作日志、落盘顺序和双进程测试矩阵。但库写入是从主线程同步调用的，没有找到进程内第二个索引写入者；用户本机只有一份 App；并且 v0.4 §4.2 已决定禁用全部递归删除，而被复现的两个故障都发生在删除路径上。
3. **两套数据模型同时有效。** G0 v1.4 §4 按"保留每次修改历史并选择采用哪个值"写，新数据库 v0.2 §3 按"只有当前值"写；D6-B 中 G3a、T02、T07、G5 的验收仍是前者。

附带后果：`main` 上"Registry 缺一行就递归删除样品目录"的真实风险（`LibrarySyncService.swift` 的 `applyBatch` / `applyAll`）已在 PR #195 中修复，却因为叠在 #194 上并被补充设计卡住而没有进入 `main`。

## 2. 用户 2026-11-11 确认的三项决定

| 决定 | 内容 | 直接影响 |
|---|---|---|
| 单写者 | 同一个 Library 同一时间只有一个 SpinLab 进程可写；第二个实例只读打开并提示。用户本机只有一份 App，也不会绕过 SpinLab 改文件。 | G1-01 补充设计 v0.1–v0.4 的跨进程协调、Root 身份登记、pending/completed 日志和恢复栅栏不再需要。 |
| 元数据存储 | 新增的记录（链接表，以及 Source / Dataset / Result / Plot / Snapshot / Attachment 的登记信息）存入 SQLite；测量数据等大文件仍放在文件夹；现有旧库不迁移、不改写，继续只读兼容。Parameter 不在其中，见第 2a 节。 | "要么全部保存、要么完全没改"、重试不重复、并发校验由数据库事务提供，不再自己设计。 |
| Parameter 只有当前值 | 修改经一次明确确认后覆盖（输入数字本身不生效，确认后才保存，防止误触）；不保留逐次修改历史；需要留存时由用户主动保存快照。 | G0 v1.4 §4 以及 D6-B 中 G3a、T02、T07 按"修订 / 采用"写的验收不再适用；D6-A §7.1–7.2 需按此改写。 |

## 2a. 数据骨架与执行材料

数据骨架、任务顺序和每个任务的需求已整理到 [`../execution/`](../execution/README.md)，派任务时以那里为准。骨架只在 [`../execution/SKELETON.md`](../execution/SKELETON.md) 一处维护。

整理执行材料时，在读过代码之后对最初的想法做了两处调整，均已告知用户，并以执行材料为准：

- **顺序：** PR #195 的安全守卫直接搬到 `main` 会在第一个提交就冲突，因此先完成并合并 PR #194，再合并 #195。
- **Parameter 存放位置：** 最初设想 Parameter 的当前值也进 SQLite，并由参数任务带入 SQLite。读代码后改为存在样品自己的 `sample.json` 里（新增一个可选字段，沿用现有的样品编辑保存路径）。原因是参数任务还不需要链接表，这样不必为它引入新的存储，旧样品也不用先补编号。SQLite 推迟到第一个需要链接表的任务（AFM 入库）再引入。

## 3. 建议顺序

1. **停止 G1-01 补充设计。** v0.4 不再送审，保留为历史材料。
2. **加单写者锁。** 打开 Library 时取得进程级独占锁，取不到则只读。独立小改动，没有前置，建议最先做。
3. **收口 PR #194 并合并。** 待修：`sampleId` 不再由批次加衬底拼接并据此去重（与 2026-11-09 的"创建几个就是几个"冲突）；评审意见 F001（旧样品被误判为手工样品而冻结）与 F002（测试改写真实设置文件）。这一步已包含 G2 的最小部分：UUID 身份、不依赖属性的目录定位、创建幂等。
4. **合并 PR #195 的安全守卫。** #194 合并后把它变基到 `main`。保留：Registry 缺行或改键在写入前拒绝、全部递归删除暂时禁用、只读预检不写文件。评审意见 F001 因删除已禁用而不可达，按此说明关闭。
5. **手填参数（T02）。** 确认后直接覆盖，存在 `sample.json`，不引入 SQLite。
6. **之后按功能纵向推进：** T03（AFM 标准入库，引入 SQLite 和链接表）→ T04 → T05。每个功能只带自己需要的基础，不单独先建"数据库基础"关卡。"输入变了、结果过期"先做成直接标记过期；快照第一版先做成"输出加当时输入值的一份拷贝"。新数据库 v0.2 §5、§7 的传递失效与依赖闭包留到出现两级结果依赖的真实功能时再做。

## 4. 文档与流程

- 把第 2 节三项决定并入 D6-A，形成一份可以直接修改的现行基线；新数据库 v0.2 的六条已确认原则并入其中，不再作为平行合同存在。
- D6-B 的启动顺序由第 3 节替代；任务卡 T01–T13 的功能目标保留，G3a、T02、T07 的验收按"只有当前值"改写。
- 独立设计审查只保留给三类改动：真实 Library 的迁移、真实数据的删除、存储格式变更。其余改动走代码评审和测试。
- 设计审查最多两轮。第二轮仍未通过时缩小范围，不再增加规范。评审意见先按"在当前使用方式下是否可达"过滤。

## 5. 仍然有效、不因本计划改变

- G0 v1.4 的身份原则：`sampleUID` 永久不变；属性相同不代表同一个样品；资产与归属关系分开；解除关联不等于删除资产。
- 递归删除在删除政策（G0 的 O-ID3）确定之前保持禁用。
- 原始测量文件不被改写；接入只做格式标准化，不做科学处理。
- 技术债的生命周期只在共享 TASK_BOARD 维护，本文件不记录债务状态。
