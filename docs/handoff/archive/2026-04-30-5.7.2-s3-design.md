### 关键设计决策

**[决策 1] 3ω physics 平铺顶层而非嵌套 `workflows/three_omega/PHYSICS.md`**

用户最初提议 "docs/architecture/workbench/ 下的 3w 的 workflow 下"——即嵌套 `workflows/three_omega/`。Codex 评审反对嵌套（high finding #2）。理由：

- 3ω 物理推演是 **domain reasoning**，与 shell / search / persistence 同层，不是 "workflow 内部细节"
- 当前只 3ω 有深度物理文档，AMR/PHE 与 XY Rotation 没有；建 `workflows/<name>/` 子目录会产生两个空占位文件，违反 Inbox/Library 平铺先例
- workflow 间的契约（ingestion / pack / tag normalization）天然属于"对照关系"，单文件 `WORKFLOW_CONTRACTS.md` 比拆 3 个目录更紧凑

**调整**：3ω physics 作为顶层文件 `THREE_OMEGA_PHYSICS.md`，与 SHELL/SEARCH/PLOT/PERSISTENCE 平级。`WORKFLOW_CONTRACTS.md` 内 3-Omega AHE 段以指针引用 `THREE_OMEGA_PHYSICS.md`。

**Jack 已知风险点**：此调整偏离用户最初的"workflow 子目录嵌套"提议。如反对，恢复嵌套结构需重新规划 workflow 子目录的内容拆分（占位文件如何避免空架）。

**[决策 2] EXTENSION_BOUNDARIES 独立成层**

Codex finding #6 指出 specs/06 的"Adding-a-new-workflow 8 步清单"是 Workbench extension 的执行入口，退役 specs/06 时若散到 SHELL 或 features.md 会丢失完整顺序。Claude 方稿弱化处理（仅在 SHELL 章节内提一笔）属于过度合并。**采纳 Codex**：单独建 `EXTENSION_BOUNDARIES.md`，集中放置 checklist + extension import rules + Domain/ExtensionPoints 边界。SHELL 文件只保留 shell 内不变式不重复 checklist。

**[决策 3] 顶层 `architecture/INDEX.md` Workbench 段降级为 dispatch summary**

Codex finding #7 指出 Inbox/Library 抽取后顶层 INDEX 已是 region 派发，Workbench 段若继续保留 first-read 表会造成双入口双维护。Claude 方稿"保留 SP-* 风险表"属于半收口。**采纳 Codex**：顶层 INDEX 的 Workbench 段缩为：region summary 一行 + 指向 `workbench/INDEX.md` + SP-* / G-* 风险一行摘要。详细 first-read 表、reading order、tests 入口全部转入 `workbench/INDEX.md`。
