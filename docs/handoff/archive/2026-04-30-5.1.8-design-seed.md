## 1. s1-design 必拍板问题

### A. 产品语义（决定数据模型形状）

Condition kind 的本质是哪种？

| 选项 | 本质 | 数据模型 |
|---|---|---|
| **选项 1** | 互斥活动模式 + 保留非活动配置（任一时刻只一种 kind 在用，另一种规则保留但不参与匹配）| enum + associated payload（更强语义，inactive payload 单独存储）|
| **选项 2** | 同一 condition 下两个独立规则分区（两种规则**同时存在**，UI 分两区编辑）| 两字段方案成立（候选 `unitSuffixSpecs` + `tokenMapRules`）|

s1-design 必须先拍板这个语义，再决定 schema 形状。

### B. 字段命名（仅在选项 2 成立时）

候选：
- `unitSuffixSpecs: [MatchSpec]` + `tokenMapRules: [MapRule]`
- 或更平铺命名（待 Jack / Codex 拍）

### C. 迁移歧义策略

旧 `ConditionDefinition.tokenMap` 是混合存储字段，可能含脏数据：
- `match.type == "unit-suffix"` 但 `value` 非 `$MATCH`
- 大小写 / 拼写变体
- 同一 rule 兼具两种语义形态

**默认策略**：精确 `unit-suffix` 进入 unitSuffix 字段；其余规则保留到 token map 字段；**歧义条目不得静默丢弃**——必须 backup + migration warning / audit log。

s1-design 须确认：
- "精确"的判定边界（仅 `match.type == "unit-suffix"` 还是同时检查 value 形态？）
- audit 落点（migration_state？专门的 migration warnings 文件？）
- 迁移失败的回滚路径

## 2. v5→v6 schema 边界

旧 schema decoder **只能存在于 migration / bootstrapper 层**：

- runtime domain model 不暴露旧 `tokenMap` 字段
- Rules Panel draft 不暴露旧字段
- RuleLoader 正常读取路径不暴露旧字段

迁移完成后，旧解码路径必须从生产代码删除——只保留在 RulesBootstrapper 私有迁移函数内（参照 5.1.5 s12 的迁移代码组织）。

---

## 3. binding 层简化的边界

**可删（跨 kind 耦合）**：

- `unitSuffixSpecsBinding` getter 里读 `tokenMap` 全表后过滤
- `tokenMapRulesBinding` setter 里 preserved unit-suffix 规则的合并逻辑

**不能删（UI 内部行为）**：

- 分区内规则的显示顺序维护
- stable IDs（编辑时不让行错位）
- section-local edit semantics（焦点 / 选中 / 取消）

## 4. 测试覆盖详单

s1-exec 必须补充三类测试，否则 AG4 不通过：

### (a) v5 mixed fixture 迁移测试

- 含混合规则的旧 `tokenMap` 文件能解码并按规则分流到两个新字段
- 含歧义条目的文件迁移后产生 audit warning，原数据保留在 backup 文件
- 迁移幂等性：迁移已迁过的文件不再产生新变化

### (b) v6 fixture decode/encode round-trip 测试

- 写两字段 → 序列化 → 反序列化 → 两字段独立存在
- 字段不互相影响（写 unitSuffix 不影响 tokenMap，反之亦然）

### (c) Rules Panel 持久化测试

- 用户在 UI 切换 kind 后保存，文件中不含旧 `tokenMap` 字段
- 多次保存的文件结构稳定

V515ConditionKindSwitchTests 重写为契约测试（守"两字段互不影响"），原 4 个回归用例的用户可见行为仍守。

---

## 5. UI 一致性具体口径

切换 kind 后回到原分区，验证：

- 规则显示顺序与切换前一致
- 选中状态 / 编辑焦点不打乱
- 分区内增删改操作位置稳定
- 删除的是跨 kind 过滤合并逻辑，不是 UI projection / order 维护
