## 2. 双 lens 审计执行步骤（每个抽样文件）

每个文件按以下 7 步走。

### Step A — 取 Code Map 声明

从对应 `docs/architecture/workbench/<layer>.md` 的 Code Map 段抓出该文件那一行注释（即 ROADMAP「稳定职责」），填入产出表临时工作表第 1 列。

### Step B — 调用链 lens（可执行检查清单 [HARD]）

> 修订自 s1 F-3：原 "grep TypeName + 反向 grep" 太宽泛会让两 AI 给出不同结论。

每个文件按下表逐项记录（**排除注释 / 测试 / Preview / Code Map 文档**）：

| 检查项 | 命令 / 信号 | 记录字段 |
|---|---|---|
| 1. Imports | `head -n 50 <file>` 抓 `^import` | `imports: [Foundation, SwiftUI, ...]` |
| 2. 类型声明 | grep `^\s*(public\|internal\|fileprivate\|private)?\s*(final\s+)?class\|^\s*struct\|^\s*enum\|^\s*actor` | `decl: [Type1, Type2]` |
| 3. 协议 conform | grep `:\s*<ProtocolName>\b` 在声明行 | `conforms: [Capability1, ...]` |
| 4. 初始化点（被谁 init） | `grep -rn "<TypeName>(" Sources/ \| grep -v "<owning_file>"` 排除自身 | `initialized_by: [files...]` |
| 5. 方法/属性调用点 | `grep -rn "\.\w*(<known_method>\|<known_property>)" Sources/` 抓主要 public surface | `called_by: [files... + 调用形态]` |
| 6. 跨层 / 跨区 caller | 对 4/5 结果按 architecture 区/层映射判定 | `cross_layer_callers: [...]` |
| 7. 反向：本文件调谁 | grep 出现的外部类型名（按 imports + decl 之外的 `\.\w+(` 调用模式） | `calls: [Type → method]` |

判定输出：
- **Boundary OK** → 调用链与声明层职责匹配，所有 caller / callee 都在合理区/层
- **Boundary Suspect** → 出现以下任一信号（每个 suspect 必须附 `caller → callee → 行为类型` 三元组）：
  - UI 层文件直调 service / repository / parser（应过 store / use case）
  - Parser 调 service / repository
  - Domain / UseCase 文件 import 了 SwiftUI
  - 跨区 caller 不在 INDEX 注册过的 `SP-*` 名单内
  - FeatureStore 之外的"非 AppState 类"持有跨 store 协调逻辑

### Step C — 实际行为 lens（行为信号表 [HARD]）

> 修订自 s1 F-4：原信号表只覆盖 UI/service/parser/AppState/ViewModel 局部，漏 FeatureStore / Concurrency / DI / Domain placement 硬约束。完整版按 CLAUDE.md `## Architecture Patterns` / `## State Management` / `## Concurrency` / `## Dependency Injection` / `## Layered Architecture` / `## View Layer` / `## Domain Models` 7 段汇总：

| # | 行为信号 | 命中含义 |
|--:|---|---|
| 1 | `@Observable` 类的 setter 含副作用（写文件 / 触发 task / spawn Task） | 违反「Side effects must not occur inside @Observable state setters」|
| 2 | UI 文件含排序 / 过滤 / 归一化逻辑 | 违反「Views must not contain sorting/filtering/normalization logic」 |
| 3 | Parser 调 Service/Repository | 违反「Parser must not call Service/Repository」 |
| 4 | Service/UseCase 含 `import SwiftUI` | 违反「Services and UseCases must have no SwiftUI import」 |
| 5 | Repository/Store 含业务策略分支（不只是 CRUD） | 违反「Repository: persistence only, no business policy」 |
| 6 | 静默 `try?` 在 service / repository / storage 层 | 违反「Never use try? to silently discard errors」 |
| 7 | AppState 方法含 `await` / `async` 标记 | 违反「AppState methods must remain synchronous」 |
| 8 | ViewModel 拥有 canonical domain model（非 transient UI state） | 违反「ViewModel must not own canonical domain models」 |
| 9 | 新 feature state 直挂 AppState raw property（非 FeatureStore） | 违反「New feature state must be introduced through a FeatureStore」 |
| 10 | observable store 不是 `@MainActor @Observable final class` | 违反「Interactive observable stores: @MainActor @Observable final class」 |
| 11 | 出现 `ObservableObject` / `@Published` / `@StateObject` / `@EnvironmentObject` / Combine 管道用于状态流 | 违反「Use @Observable macro exclusively」 |
| 12 | Repository 用非 `AsyncStream` 推送变更（如 PassthroughSubject / NotificationCenter / DispatchQueue） | 违反「Repositories: AsyncStream + Continuation. Never Combine」 |
| 13 | 重 I/O 直接在 `@Observable` 类方法体内（非 data actor） | 违反「Heavy I/O: run inside data actor, not inside @Observable classes」 |
| 14 | `@Observable` 类方法标 `async` | 违反「@Observable class methods must not be async」 |
| 15 | 运行时副作用依赖未经 `AppEnvironment` 注入（直 instantiate concrete service） | 违反「All runtime dependencies with side effects declared in AppEnvironment」 |
| 16 | UseCase 持有 storage 细节 / state | 违反「UseCases: stateless structs, receive dependencies as function parameters」 |
| 17 | Domain model 定义在 `Features/` 而非 `Domain/` | 违反「Domain models live in Domain/. Do not define inside Features/」 |
| 18 | View 接收 AppState 通过 init 参数（非 `@Environment`） | 违反「Views receive AppState via @Environment. Never pass as init parameter」 |

### Step D — 三分类落格

依 ROADMAP「三分类发现 + 处置策略」判定该文件归类（Violation / Drift / Accepted Boundary）。

### Step E — Drift 注释当场修订（仅当 D 判定为 Drift）

按 CLAUDE.md「Adding New Swift Code」第 4 步注释体例改 Code Map 行：
- 主动短句，描述稳定职责
- 不写条件从句、临时实现原因、测试结论、调用方信息
- 长度建议 ≤ 80 字符

修订动作记录到产出表 `## 2. Doc Drift Fixed` 段，**字段必含**：file / 旧注释 / 新注释 / 修订理由 / commit_id（修订 commit 的 sha）。Drift 修订必须每条独立 commit，便于评审方对照修改前后差异。

### Step F — Cross-Region Doubt 顺手抓（仅当跨区现象自然出现）

不分支去做完整链调查；仅当 Step B/C 顺手扫到跨区不一致 / 链级语义疑点 / 多文件共漂移时，写一行进 `## 4. Cross-Region Doubts For 5.1.14` 段：现象 + 涉及文件 + 一句猜测。

### Step G — 入产出表

按归类写入产出表对应段（详见 §3）。

## 4. 工作切分与双 AI 协作

按 CLAUDE.md feedback `balanced` 规则切。核心是：抽样池一旦封闭，按文件分批，双方各扫一半——抽样独立 + 互不污染 + 收尾对账。

### 4.1 切分策略

| 批次 | 抽样池子集（按层） | 主审方 | 评审方 |
|---|---|---|---|
| Batch 1 | Shell + Render | Claude | Codex |
| Batch 2 | Workflow（45 条最大层） | Codex | Claude |
| Batch 3 | Search + Persistence + Extension | Claude | Codex |

> 跨批"非抽样池"文件：批次列出的层不等于该层全审，**只审 Audit Sample 命中的子集**；评审方对主审方做"漏审"挑战时只允许针对 Audit Sample 范围内的遗漏。

### 4.2 评审动作（分层抽查 [HARD]）

> 修订自 s1 F-6：原"30% 随机抽查"会漏掉低数量但高风险的 SP/G/cross-cutting 样本。

每批主审方完成后：

1. 主审方提交批内产出（写入产出表对应段，commit 一次）
2. 评审方按下表分层抽查：

   | 子集 | 抽查比例 |
   |---|---|
   | 主审方判 Violation 的所有行 | **100% challenge**（每条独立追问） |
   | SP-* 命中样本 | **100% 复核**（不论主审方判 OK / Suspect / Drift） |
   | G-* 命中样本 | **100% 复核** |
   | Cross-cutting 归属样本（主 owner Workbench 但跨区行为） | **100% 复核** |
   | 其余样本 | 每层至少 30%，随机抽 |

3. 评审方在产出表批次后追加 `### Batch <n> Review by <party>` 子段，记录 challenge / 接受 / 补充 Violation
4. 双方收敛后才进入下一批

### 4.3 收尾对账

三批扫完，全员复审：
1. Audit Sample §0 是否每条都有归类（不允许悬空）
2. Drift 注释修订是否全部已 commit 到对应 architecture 文档（带 commit_id 字段）
3. Cross-Region Doubts 段是否每条都有"涉及文件 + 一句猜测"完整字段
4. Fix-Round Draft 是否能直接喂给 5.1.11b（next_action / 修复粒度 / 依赖三列齐全 + 只含 11b/11c/d 行）

## 7. 风险预案

| 风险 | 表现 | 处置 |
|---|---|---|
| 抽样池太大，a 轮拖延 | Step 0 后 Candidate Pool 命中（强信号去重后）≥ 60 条 | 砍掉 churn < 5 + 非 SP/G 关联条目，target Audit Sample 35–45 |

| Violation 数量爆表（≥ 20 条） | 产出表 §1 行数失控 | 11b 自然进入 c/d 拆批；不在 a 轮调整规则 |
| 出现链级问题但跨 2+ 区 | Cross-Region Doubts §4 出现 ≥ 5 条 | 全部喂给 14a；本轮不分支调查 |
| Drift 注释修订与 5.7.x 在写代码冲突 | 同文件 Code Map 行被两轮同时改 | a 轮在 5.1.11 分支独立工作；如确有冲突，merge 时以 a 轮的"职责描述准确性"为优先 |
| **Drift 修改与审计结论时间错位** | 评审方难以判断结论是否基于修订前/后 Code Map | Drift 修订必须每条独立 commit + 产出表 §2 含 commit_id；评审以"修订前 Code Map 与当前 code 的差异"为准 |
| Codex 不可用（rate limit / 故障） | 评审方失效 | 单 AI fallback：Claude 主审 + 申报"无对抗评审"，等 Codex 恢复后补评审；**禁止在补评审完成前进入 11b**（ROADMAP "a 完才开 b" 依赖对抗评审闭环） |
