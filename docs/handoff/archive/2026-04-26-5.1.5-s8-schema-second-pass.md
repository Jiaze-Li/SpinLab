## 1. 目标 schema（v2）

### 1.1 measuring_condition.json（v1→v2）

```json
{
  "version": 2,
  "batch": {
    "preferSampleId": true,
    "fallbackPatterns": ["^(B|Batch)\\d+$"]
  },
  "conditionDefinitions": [
    {
      "id": "device",
      "label": "Device",
      "kind": "token_map",
      "tokenMap": [
        { "match": {"scope": "tokens", "type": "equals", "matchValues": ["wafer"]}, "value": "wafer" }
      ]
    },
    { "id": "temperature", "label": "Temperature", "kind": "unit_suffix",
      "unitPattern": "^-?\\d+(?:\\.\\d+)?(?:K|k|C)$" },
    { "id": "current",     "label": "Current",     "kind": "unit_suffix",
      "unitPattern": "^-?\\d+(?:\\.\\d+)?(?:mA|A|uA)$" },
    { "id": "field",       "label": "Field",       "kind": "unit_suffix",
      "unitPattern": "^-?\\d+(?:\\.\\d+)?(?:T|mT|Oe)$" },
    { "id": "shift",       "label": "Shift",       "kind": "unit_suffix",
      "unitPattern": "^-?\\d+(?:\\.\\d+)?(?:shift)$" }
  ]
}
```

约束：
- `kind == unit_suffix` 必须有 `unitPattern`，**不得**有 `tokenMap`
- `kind == token_map` 必须有 `tokenMap`，**不得**有 `unitPattern`
- `label` 用户定义，**不**自动改写
- 注：`MatchSpec.value/values` 同步改 `matchValues: [String]`（见 §1.4）

### 1.2 sample_identification.json（v1→v2）

```json
{
  "version": 2,
  "sampleId": { "patterns": ["^(PN|PT|SL)\\d+$"] },
  "substrate": {
    "tokenSeparators": "_- ()",
    "substrateTagRules": [
      { "match": {"scope": "tokens", "type": "equalsOrContainsAny", "matchValues": ["HF"]}, "value": "HF" },
      { "match": {"scope": "tokens", "type": "equalsOrContainsAny", "matchValues": ["BAKE","BAKED"]}, "value": "baked" },
      { "match": {"scope": "tokens", "type": "equalsOrContainsAny", "matchValues": ["ORIGIN","ORIGINAL"]}, "value": "o" },
      { "match": {"scope": "tokens", "type": "equals", "matchValues": ["STO111"]}, "value": "STO 111" }
      // ... 其余 substrateTagRules 不变（命名同步迁 matchValues）
    ],
    "materials": [
      { "id": "STO",       "tokens": ["STO"],                          "aliases": [],      "displayName": "STO" },
      { "id": "NGO",       "tokens": ["NGO"],                          "aliases": [],      "displayName": "NGO" },
      { "id": "MAO",       "tokens": ["MAO"],                          "aliases": [],      "displayName": "MAO" },
      { "id": "MGO",       "tokens": ["MGO"],                          "aliases": [],      "displayName": "MgO" },
      { "id": "AL2O3",     "tokens": ["AL2O3"],                        "aliases": [],      "displayName": "Al2O3" },
      { "id": "SI",        "tokens": ["SI"],                           "aliases": ["ONSI"],"displayName": "Si" },
      { "id": "POLY-SIO2", "tokens": ["POLY-SIO2","POLY-SIO2 ON SI"], "aliases": [],      "displayName": "poly-SiO2 on Si" }
    ],
    "treatments": [
      { "id": "HF", "displayName": "HF",    "keywords": ["hf"],
        "standaloneTokens": [], "containsTokens": [] },
      { "id": "b",  "displayName": "baked", "keywords": ["b","bake","baked"],
        "standaloneTokens": [], "containsTokens": [] },
      { "id": "o",  "displayName": "o",     "keywords": ["o","origin","original"],
        "standaloneTokens": ["o"], "containsTokens": ["origin","original"] }
    ],
    "orientations": {
      "pattern": "\\d{3}",
      "rows": [
        { "id": "001",  "tokens": ["001"],  "aliases": ["100"] },
        { "id": "111",  "tokens": ["111"],  "aliases": [] },
        { "id": "110",  "tokens": ["110"],  "aliases": [] },
        { "id": "0001", "tokens": ["0001"], "aliases": [] }
      ]
    }
  }
}
```

字段语义：
- `materials[].tokens`：识别用 token 列表（多个 token 命中同一 material）
- `materials[].aliases`：备用别名映射（其他 id 指向本 material）
- `materials[].displayName`：显示文案；用户定义不改写
- `treatments[].keywords`：触发该 treatment 的关键词
- `orientations.rows[].aliases`：等价 orientation 标准化（如 `100→001`）
- `substrate.shared` 容器**整删**

### 1.4 MatchSpec 命名统一（5 schema 全文）

```swift
struct MatchSpec: Decodable {
    var scope: MatchScope
    var type: MatchType
    var matchValues: [String]   // 新：统一数组形态
}
```

迁移：
- v1 `value: "X"` → v2 `matchValues: ["X"]`
- v1 `values: ["X","Y"]` → v2 `matchValues: ["X","Y"]`
- 校验：`type == equals` 且 `matchValues.count != 1` → fail-fast warning

### 1.5 conditionFieldIDs → conditionFieldIds 改名（条件性）

**必做前评估**：grep 全仓 `conditionFieldIDs` 命中点估算时间。

不做时 v2 schema 仍用 `conditionFieldIDs`（不破坏 s7 已落地 WorkflowDefinitionStore）。

## 4. 迁移代码思路（RulesBootstrapper v1→v2）

### 4.1 入口

在 `RulesBootstrapper.seedMissingRuntimeFilesFromBundleIfNeeded()` 前置：`migrateRuntimeRulesToV2IfNeeded()`。

启动流程：
1. 检测 runtime 5 本子是否齐全 + `version >= 2`；满足 → 直接返回（幂等）
2. 否则读 runtime（缺则 bundle 回退）v1 数据 → 组装 v2 内存对象
3. 写临时目录 `config/.migration-tmp-<timestamp>/`
4. 逐文件 decode-verify
5. 全部 verify 成功 → atomic replace 到 config 目录
6. 写 `config/.migration_state.json` 标记完成

### 4.2 备份策略

迁移前备份到 `config/.backup-<timestamp>/`：
- 5 本子现有文件（存在即备份）
- `library_import_rules.json`（涉及 §1.6 清理）

`migration_state.json` 字段：
```json
{
  "rules_schema_version": 2,
  "migrated_at": "2026-...",
  "source_sha256": { "<filename>": "<hex>" },
  "target_sha256": { "<filename>": "<hex>" },
  "warnings": [
    "measuring_condition: dropped dirty binding for id=foo (kind/binding mismatch)"
  ]
}
```

### 4.3 幂等与失败保护

幂等键：`migration_state.rules_schema_version >= 2` 且 5 本子 hash 与文件实际一致 → 跳过迁移。

任一文件 verify 失败：
- **不**覆盖正式文件
- 写 `migration_failed.json`（含失败文件 + 错误摘要）
- 保留 `.backup-*` 供人工回滚
- 启动时 RulesPanel 顶部显示 degraded banner

### 4.4 脏数据处理（§0 #11）

v1 `conditionDefinitions` 转 v2 时遇到 `kind/binding` 不一致：
- 优先按 `kind` 决定字段（kind=unit_suffix 写 unitPattern；kind=token_map 写 tokenMap）
- binding 指向不存在的 dict key → 跳过该条 + warning
- 同 id 重复条目 → 保留首条 + warning

所有 warning 写入 `migration_state.warnings`，启动后 RulesPanel 可见。

### 4.5 兼容读取窗口（§0 #10）

不留兼容期。v2 落地后：
- Decoder 只接受 v2 schema
- v1 文件触发迁移流程（§4.1–4.4）
- 迁移完成后 v1 文件已被 atomic replace，runtime 不再可能读到 v1
- 兼容读代码（仅迁移函数内部用）跟着 v2 一起 ship

### 4.6 兼容期清理

迁移成功后清理 `config/.migration-tmp-*`（保留 `.backup-*` 至少一代供回滚）。

## 7. 风险点（s9 实施前 reread）

1. **substrate 36 文件 touch surface**：C3a/C3b 拆分能并行，但单 commit 仍可能触 10+ 文件。实施时按文件分批 grep + Read，避免单次 commit 过大难评审
2. **MatchSpec 改名牵连测试 fixture 极广**：C1 之前先跑 `swift test` 留 baseline；C6 后逐文件比对失败原因，区分"回归"vs"fixture 漂移"
3. **displayLabels 删之前 grep 实证**：C1 实施前 grep 全仓 `displayLabels` 写入路径（非 builtin 来源），如发现用户写入路径需停下报告 Jack（s3 §10.5 已挂"待证据"）
4. **library_import_rules substrate 重复段实证**：C6 删之前先 grep `substrateMaterialTokens` / `substrateProcessingKeywords` Swift 端消费方，决定切/删
5. **conditionFieldIDs→Ids 范围评估**：C6 评估时间 grep 命中数；超 2h 立刻撤回本期
6. **v1 dirty data**：迁移代码必须警告 + 跳过脏条目，不得静默丢规则
7. **needle map 索引**：substrate 数据当前 7-10 row 性能无问题，但 `compile()` 必须建索引（材料 token → MaterialDefinition），否则未来扩到 50+ row 时线性扫描慢
8. **atomic replace 失败语义**：tmp 目录写文件 → verify → atomic replace 中任一步失败必须保正式文件不动 + 写 migration_failed.json，不得半迁移
