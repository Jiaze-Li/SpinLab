## 1. 背景与动机

### 1.1 现状问题

Inbox 一个功能区的代码描述按「文档类型」散布在 4 处：
- `specs/03_PARSER_ROUTING_RULES.md` — 解析/路由算法（消费层）
- `features.md` Rules Panel/Auto-Sync/Bootstrap/Inbox 四段 — 编辑 UI + Apply 行为（编辑层 + 工作流层）
- `architecture/import/` 两份 — Layer 边界 + 5 阶段 flow（消费层细节）
- `specs/02_DATA_RULES.md` 部分 — sidecar 字段 + tag 标准化（输出契约层）

改 schema 时多处要同步，漂移成本高。Apply 行为已经在 `features.md` 和 `specs/05`（已 archive）漂过一次。

### 1.2 拍板方向（Jack 已确认）

文档分类从「文档类型」切换到「功能区 × 层」：
- **specs/** = 跨域契约：PO 承诺、跨域领域模型、design tokens
- **docs/architecture/<region>/** = 单功能区的所有层（编辑 UI / 消费算法 / 输出契约 / 工作流行为）

首发 Inbox，验证模式后再做 Library / Workbench。

## 2. 目标文件结构

```
docs/architecture/inbox/
  INDEX.md                  Inbox 子系统派发入口（分层说明 + 阅读顺序）
  RULES_AUTHORING.md        编辑层：Rules Panel 5 段、Save 语义、Auto-Sync、Bootstrap
  ROUTING_PIPELINE.md       消费层：5 阶段 layer 边界 + Evaluate flow + parser/route/match 算法 + queue verdict
  CONFIRM_AND_APPLY.md      工作流层：pending queue、draft confirm、Apply/Apply All、Clear Imports、audit 时序
  OUTPUT_CONTRACTS.md       契约层：sidecar 字段、tag normalization、registry lookup、Inbox→Library 写边界
```

5 份。`INDEX.md` 仅做派发，其余 4 份对应 Inbox 的 4 个层。

**架构层 vs 工作流层为什么分开**：CONFIRM_AND_APPLY 描述的是用户操作行为（按钮触发、原子性、回滚时序），OUTPUT_CONTRACTS 描述的是数据形态（字段 schema、normalize 映射）。两者不同维度——把 Apply 时序塞进 sidecar 文档会污染契约形状描述。

## 11. Code Coverage Meter（详细方案）

> 收敛源：Claude 方初稿 + Codex 独立设计（[`tmp/codex-design-572-coverage.md`](../../tmp/codex-design-572-coverage.md)，95 行）+ 对抗 fixes。

### 11.1 计量器位置与格式

放在 `docs/architecture/INDEX.md` 顶部 Status/Source 行之后、How To Use 段之前：

```markdown
> **Code coverage**: <N>/218 source files mapped. Last verified: <YYYY-MM-DD> by `scripts/verify_architecture_code_coverage.sh`.
```

- denominator 218 = 当前 `find Sources -name '*.swift' -type f | wc -l` 实际值
- numerator = `architecture/**/*.md` 中 `## Code Map` 段反引号包裹、`Sources/...swift` 结尾的唯一路径数
- Last verified 日期手动同步更新（**Fix #3：不进 script 强校验**）

### 11.2 verify 脚本设计

新增 `scripts/verify_architecture_code_coverage.sh`，纯 bash + awk/sed。

**扫描范围**：
- 仅扫 `docs/architecture/**/*.md`
- **排除** `docs/architecture/REGION_MAP.md`（历史扫描底稿，不算子文档）
- 仅取每份文档中 `## Code Map` 段（从该标题后到下一个 `## ` 同级标题或 EOF）
- 段内 fenced code block (` ``` `) **不算**（防示例污染）

**路径提取规则**：
- 反引号包裹的字符串
- 必须 `Sources/` 开头
- 必须 `.swift` 结尾
- 目录路径不展开为文件（不让 numerator 虚高）

**去重策略**：
- 仓库根目录相对路径为 key
- 同一文件多处出现只计 1 次
- 重复引用列 warning 但不阻塞 commit

**校验逻辑**：
1. 每个被计入的路径必须存在且是普通文件
2. denominator 现算（`find Sources -name '*.swift' -type f | wc -l`）与脚本内 `EXPECTED_TOTAL=218` 比较，不一致 fail（**发现新增/删除 Swift 文件后忘维护进度基线**）
3. INDEX coverage 行 numerator 数字与 script 计算的 mapped count 一致（仅校验数字，不校验 `Last verified` 日期）

**输出格式**：

成功：
```
[architecture-coverage] mapped=20 total=218
[architecture-coverage] index="20/218 source files mapped"
[architecture-coverage] PASS
```

失败示例：
```
[architecture-coverage][error] Missing mapped file: Sources/SpinLabApp/Foo.swift
[architecture-coverage][error] Sources Swift total changed: expected=218 actual=219 — update EXPECTED_TOTAL and INDEX
[architecture-coverage][error] INDEX coverage numerator mismatch: index=20 actual=19
```

**退出码**：
- `0`：路径全存在、denominator 一致、INDEX 数字同步
- `1`：任一项失败

### 11.3 pre-commit 集成

新增 `scripts/install_git_hooks.sh`，安装 hook 到 `.git/hooks/pre-commit`。

**安装逻辑**：
- `git rev-parse --git-path hooks/pre-commit` 取得路径（兼容 worktree）
- 不存在 → 创建 shell hook
- 已存在 → 在尾部追加带 sentinel 的 block：
  ```sh
  # spinlab-architecture-coverage:start
  ./scripts/verify_architecture_code_coverage.sh
  # spinlab-architecture-coverage:end
  ```
- sentinel 已存在 → 不重复追加

**hook 强度**：
- 强约束：路径存在、denominator 同步、INDEX 数字同步
- 不强制 `--no-verify` 绕开（符合项目 git 安全规范）
- 不校验语义正确性（成本太高，本轮目标外）

**Fix #4 关联**：hook 不自动安装，README 加指引让新 dev 手动跑 `install_git_hooks.sh`。

### 11.4 设计权衡（采 Codex 否决理由）

| 备选 | 否决理由 |
|---|---|
| 计量器分散到每子文档 | 用户只要全局数字粒度；分散容易出现多个数字不一致 |
| 脚本自动重写 INDEX coverage 行 | 引入文档自动改写规则、日期格式管理；本轮低成本目标下，"数字同步校验"够 |
| 目录路径自动展开为 .swift 文件 | numerator 虚高（未被逐文件描述也算进去）；目录可在 Code Map 文字说明保留，但不进数字 |
| CI 强制（GitHub Action）替代 pre-commit | 用户明确说 pre-commit；未来上 CI 时调用同一脚本即可 |
