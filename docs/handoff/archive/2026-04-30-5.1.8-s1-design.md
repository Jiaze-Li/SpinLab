# 5.1.8 s1-design — Condition 统一规则列表 handoff

Status: pending execution
Scope: design only. s1-exec 按本文执行；本文不含生产代码改动。

## 0. 总决策

Condition 不再是 `unit_suffix` / `token_map` 二选一模式。新模型是单一 `matches: [MapRule]` 规则列表，每条规则自己携带 `match.type` 与输出 `value`。

- Condition allowedOps 固定为 `[.equals, .contains, .unitSuffix]`。
- `.unitSuffix` 行的输出语义固定为原文：物理 JSON 仍写 `value: "$MATCH"`，UI 自动注入并灰显。
- `.equals` / `.contains` 行输出由用户编辑。
- 所有行按源文件顺序同时参与匹配，first-match wins。没有隐藏分区，没有 inactive payload。
- Batch ID / Substrate / Condition 的差别只通过同一编辑器的 allowedOps + outputBehavior 表达。

---

## 1. v5 → v6 schema 迁移路径

### 1.a 决策 + 理由

**决策**：迁移落点放在 `RulesBootstrapper` 的私有 JSON migrator 中，新增 `migrateMeasuringConditionV5ToV6IfNeeded(json:warnings:)`，并把 `measuring_condition.json` 文件版本升到 `6`。不要把旧 shape 兼容放进 runtime decode，也不要让 `RulesManagementStore` draft 长期兼容旧字段。

理由：
- 这是 runtime-loaded config 的结构迁移，不是临时 UI decode 兼容；启动时一次性升级能保证 RuleLoader、Rules Panel、runtime 只面对 v6 canonical shape。
- 项目已有 s12 风格：`RulesBootstrapper` 负责 backup / tmp / verify decode / warning state，旧 schema decode 私有化，符合 seed 的 schema 边界。
- 当前 `.migration_state.json` 的 `rules_schema_version` 已可能是 `6`，不能只靠 state guard 判断已迁移。s1-exec 必须改 skip 条件：即使 state version >= 6，也要读取 `measuring_condition.json.version`；若文件版本 < 6，必须继续执行 measuring migration。可选择把 composite state bump 到 `7`，但文件内 schema 仍是 `version: 6`。

**旧 unit_suffix kind 下 equals/contains 规则**：迁移为 `MapRule(match: oldSpec, value: "$MATCH")`。理由是这些规则在旧 UI 的 unit_suffix 模式下没有用户可编辑 output，语义就是“输出命中原文”；按 op 分别填空会改变可见结果。

**旧 token_map kind 下隐藏的 unit-suffix 脏数据**：必须携带到新统一列表，位置保持在旧 `matches` / `tokenMap` 数组原位置，不重排。它们迁移为 `MapRule(match: oldRule.match, value: "$MATCH")`；如果旧行已有非空 `value` 且不是 `$MATCH`，改写为 `$MATCH` 并写 warning。理由是 Jack 已确认所有规则都要参与匹配；隐藏规则不是无效数据，迁移后应可见、可编辑、参与匹配。干净携带不需要 audit log；只有语义被修正或行被丢弃时写 migration warning。

**幂等性**：当 `version >= 6` 时原样返回；v6 encode/decode 不再输出 `kind`、`unitPattern`、`tokenMap`。对同一 v6 文件重复运行迁移，JSON 字段和值稳定不变。

**迁移失败回滚**：沿用 `RulesBootstrapper.migrateRuntimeRulesIfNeeded()` 的现有路径：
- tmp：`<configDirectory>/.migration-tmp-<timestamp>/measuring_condition.json`
- backup：`<configDirectory>/.backup-<timestamp>/measuring_condition.json`
- state：`<configDirectory>/.migration_state.json`
- failure：`<configDirectory>/.migration_failed.json`

失败策略：transform / encode / tmp write / verify decode 失败时不覆盖 runtime 文件；verify decode 失败写 `.migration_failed.json`。atomic replace 失败时 backup 已存在，runtime 可能部分失败，必须 `AppLogger` error，并在 `.migration_failed.json` 或 `.migration_state.json.warnings` 中保留 reason；用户可用 `.backup-<timestamp>` 手动回滚。

### 1.b 受影响代码点

- `Sources/SpinLabApp/Import/Rules/RulesBootstrapper.swift:migrateRuntimeRulesIfNeeded`
  - 调整 state skip gate，加入 measuring file version < 6 时仍迁移。
  - 在现有 v2/v3/v4 chain 后追加 v5→v6。
- `Sources/SpinLabApp/Import/Rules/RulesBootstrapper.swift:migrateMeasuringConditionV3ToV4IfNeeded`
  - 保留旧迁移，不把 v6 逻辑混入此函数。
- `Sources/SpinLabApp/Import/Rules/RulesBootstrapper.swift` 新增 `migrateMeasuringConditionV5ToV6IfNeeded`
  - 输入兼容当前 v4/v5 shape：`kind == unit_suffix` 的 flat `[MatchSpec]`，`kind == token_map` 的 `[MapRule]`，以及脏混合数据。
- `Sources/SpinLabApp/Import/Rules/RulesBootstrapper.swift:writeMigrationState` / `writeMigrationFailed`
  - warnings 继续作为 audit 落点；必要时 bump composite state version。
- `Sources/SpinLabApp/config/measuring_condition.json`
  - 升到 `version: 6`，每个 definition 只保留 `id`、`displayName`、`matches: [MapRule]`。

### 1.c 风险 / 回滚路径

风险：`.migration_state.json` 已记录 `rules_schema_version >= 6` 导致新迁移被跳过。回滚路径：s1-exec 必须先修 skip gate；测试覆盖“state 已是 6 但 measuring_condition.version < 6 仍迁移”。

风险：旧 token_map 中的 hidden unit-suffix 被带入后会开始参与匹配，可能改变历史行为。该改变符合 Jack 产品口径；回滚只能通过 backup 恢复旧 runtime config，不能在新代码保留隐藏分区。

## 2. unit-suffix 输出语义承载

### 2.a 决策 + 理由

**选择 (i)：`$MATCH` sentinel 继续存在于 `MapRule.value`。**

理由：
- runtime 已有 `firstMatchValue` / `conditionFirstMatchValue` 对 `$MATCH` 的处理，改动面小且行为明确。
- JSON 物理形态统一为 `[MapRule]`，Condition 每行都有 output 字段；没有 optional output 的非法状态。
- UI 可以在 `.unitSuffix` op 上锁定 `value = "$MATCH"`，同时仍让 `.equals` / `.contains` 编辑输出。
- enum payload 方案会引入新结构与更多 Codable 分支，但产品上已经要求三个本子统一为单一规则列表，不需要再用 enum 表达两类分区。

### 2.b 跨层影响

- runtime `FilenameRuleSet.MapRule` 保持 `{ match, value }`，但 ConditionDefinition 不再按 kind decode。
- `RulesManagementStore.MeasuringConditionFileDraft.ConditionDefinition` 改为 `matches: [MapRule]`；draft encode 永远写 `[MapRule]`。
- JSON physical shape：unit-end 行也写：
  - `{"match":{"type":"unit-suffix","value":"K"},"value":"$MATCH"}`
- UI binding：op 变为 `.unitSuffix` 时同步把当前行 `value` 设为 `$MATCH`；渲染时输出 TextField disabled，展示 `$MATCH` 或“原文”均可，但存储值必须是 `$MATCH`。

### 2.c 受影响代码点

- `Sources/SpinLabApp/Import/Rules/FilenameRuleSet.swift:ConditionDefinition.init(from:)`
- `Sources/SpinLabApp/Import/Rules/FilenameRuleSet.swift:compileConditionDefinitions`
- `Sources/SpinLabApp/Import/Rules/FilenameRuleSet.swift:conditionEvaluationWithSources`
- `Sources/SpinLabApp/Import/Rules/FilenameRuleSet.swift:conditionFirstMatchValue`
- `Sources/SpinLabApp/Features/RulesPanel/RulesManagementStore.swift:MeasuringConditionFileDraft.ConditionDefinition`
- `Sources/SpinLabApp/Features/RulesPanel/Components/MatchRulesEditor.swift`

### 2.d 风险 / 回滚路径

风险：用户手改 JSON，把 `.unitSuffix` 行 value 写成非 `$MATCH`。执行层应在 Rules Panel save validation 或 bootstrap migration 中修正并 warning；runtime compile 也应保守地按 op 类型视为 `$MATCH`，避免错误输出。回滚路径是恢复 backup config；不恢复 `kind`。

## 3. ConditionMatches / ConditionDefinitionKind 拆除范围

### 3.a Runtime

**砍**：删除 `FilenameRuleSet.ConditionMatches`、`FilenameRuleSet.ConditionDefinitionKind`、`ConditionDefinition.kind`。

**改**：`FilenameRuleSet.ConditionDefinition` 改为：

```swift
struct ConditionDefinition: Decodable {
    var id: String
    var displayName: String?
    var matches: [MapRule]
}
```

`compileConditionDefinitions` 不再 switch kind，统一 `compileMapRules(definition.matches, ...)`。`conditionFirstMatchValue` 保留 `$MATCH` 分支；遇到 `rule.match.spec.type == .unitSuffix` 时仍走 `normalizeUnitSuffixToken`。

### 3.b Persistence / Rules Panel draft

**改**：`MeasuringConditionFileDraft.ConditionDefinition` 删除 `kind`、`unitPattern`、`tokenMap`，新增 `matches: [MapRule]`。

向后兼容不放在 draft decode。Rules Panel 打开的是已由 bootstrapper 升级后的 v6 文件；如果直接 decode 旧文件失败，这是合理暴露，因为启动迁移才是唯一兼容入口。

### 3.c Migration

**留，但隔离**：旧 `kind` / `unitPattern` / `tokenMap` 解码逻辑只保留在 `RulesBootstrapper` 私有 JSON 迁移函数内。`RuleLoader.normalizeConditionDefinitionBindings` 与 `RuleCanonicalizer.normalizeConditionDefinitionBindings` 里合成 definition 的逻辑要移除 kind 依赖，或在 v6 后完全删除这条兼容路径。

### 3.d Tests

**V515ConditionKindSwitchTests 整体重写**：
- 保留用户可见契约：“编辑规则后不丢”、“行顺序稳定”、“所有规则同时参与匹配”。
- 删除旧契约：“kind round-trip”、“token_map view 隐藏 unit-suffix”、“unit_suffix-hidden-in-token_map raw storage intact”。
- `unit_suffix` 下 equals/contains 旧用例改为 migration test：迁移后这些行仍存在且 `value == "$MATCH"`。

### 3.e 风险 / 回滚路径

风险：Workbench condition source provenance 目前通过 kind 区分 `RuleRef.conditionTokenMap` / `conditionUnitSuffix`。v6 后应统一为 `RuleRef.conditionRule(id:ruleIndex:)`，或保留旧两个 ref factory 但按 op 类型而非 kind 选择。建议新增统一 ref，旧 ref 只作解析兼容。回滚路径：若 provenance 消费端尚未准备好，短期可让 `.unitSuffix` 行继续产出 `conditionUnitSuffix` ref，其余产出 `conditionTokenMap` ref，但不能恢复 kind。

## 4. UI 改动具体清单

### 4.a MeasuringConditionSection

**决策**：删除 `conditionDetail` 中 `LabeledContent("Kind")` segmented control，删除 `if def.kind == "unit_suffix" { ... } else { ... }` 分支。Condition detail 只显示 Display Name + 一个统一规则编辑器。

调用形态：

```swift
MatchRulesEditor(
    rules: rulesBinding(condIdx: idx),
    allowedOps: [.equals, .contains, .unitSuffix],
    defaultOp: .equals,
    outputBehavior: .editable(title: "Mapped to", lockedOps: [.unitSuffix], lockedValue: "$MATCH")
)
```

`defaultOp` 用 `.equals`，避免新建行默认进入锁定输出；用户需要 unit-end 时主动选。

### 4.b MatchRulesEditor / MatchMapRulesEditor 合并

**决策**：保留一个 public `MatchRulesEditor`，删除 public `MatchMapRulesEditor`。内部可以保留 private row shell。使用 `outputBehavior`，不要用 `supportsOutput: Bool`，因为 Condition 的 output 行为不是简单有/无，而是“部分 op 可编辑、unit-end 锁定”。

当前接口：

```swift
MatchRulesEditor(
    rules: Binding<[FilenameRuleSet.MatchSpec]>,
    allowedOps: [FilenameRuleSet.Operation],
    defaultOp: FilenameRuleSet.Operation
)

MatchMapRulesEditor(
    rules: Binding<[MapRule]>,
    allowedOps: [FilenameRuleSet.Operation],
    defaultOp: FilenameRuleSet.Operation,
    outputTitle: String = "Output"
)
```

目标接口：

```swift
enum MatchRuleOutputBehavior: Equatable {
    case none
    case editable(title: String)
    case editableWithLockedOps(title: String, lockedOps: Set<FilenameRuleSet.Operation>, lockedValue: String)
}

struct MatchRulesEditor: View {
    init(
        specs: Binding<[FilenameRuleSet.MatchSpec]>,
        allowedOps: [FilenameRuleSet.Operation],
        defaultOp: FilenameRuleSet.Operation
    )

    init(
        rules: Binding<[MapRule]>,
        allowedOps: [FilenameRuleSet.Operation],
        defaultOp: FilenameRuleSet.Operation,
        outputBehavior: MatchRuleOutputBehavior
    )
}
```

Batch / Substrate / Workflow matchRules 使用 `specs:` init（output `.none`）。Workflow measurementTagRules 与 Condition 使用 `rules:` init。这样调用点统一到同一个组件名，同时不强迫无 output 的本子构造 fake MapRule。

### 4.c unit-end 灰显与自动输出

实现路径：
- Row render 根据当前 op 判断 `outputBehavior.lockedOps.contains(op)`。
- 若 locked：TextField disabled，binding get 返回 `$MATCH`，set 忽略或强制 `$MATCH`。
- op picker setter 中：当新 op 是 locked op，立即设置 `rules[idx].value = "$MATCH"`；当从 locked op 切到 editable op，建议把输出清空 `""`，避免 `$MATCH` 作为普通输出泄漏。用户再自填。
- Add：若 `defaultOp` 是 locked op，初始 output 为 `$MATCH`；否则为 `""`。

### 4.d Binding 清理

**删除**：
- `unitSuffixSpecsBinding(condIdx:)`
- `tokenMapRulesBinding(condIdx:)`
- `tokenMapRuleBinding(condIdx:ruleIdx:)` 若已无调用
- 所有 preserved hidden unit-suffix 合并逻辑

**新增单一 binding**：

```swift
private func rulesBinding(condIdx: Int) -> Binding<[MapRule]> {
    Binding(
        get: {
            guard let d = draft, d.conditionDefinitions.indices.contains(condIdx) else { return [] }
            return d.conditionDefinitions[condIdx].matches
        },
        set: { newRules in
            guard var d = draft, d.conditionDefinitions.indices.contains(condIdx) else { return }
            d.conditionDefinitions[condIdx].matches = newRules.map(normalizeConditionRuleForUI)
            apply(d)
        }
    )
}
```

`normalizeConditionRuleForUI` 只做一件事：`match.type == "unit-suffix"` 时强制 `value = "$MATCH"`；不得排序、改名、改 ID。

### 4.e 受影响代码点

- `Sources/SpinLabApp/Features/RulesPanel/Sections/MeasuringConditionSection.swift:conditionDetail`
- `Sources/SpinLabApp/Features/RulesPanel/Sections/MeasuringConditionSection.swift:unitSuffixSpecsBinding`
- `Sources/SpinLabApp/Features/RulesPanel/Sections/MeasuringConditionSection.swift:tokenMapRulesBinding`
- `Sources/SpinLabApp/Features/RulesPanel/Components/MatchRulesEditor.swift:MatchRulesEditor`
- `Sources/SpinLabApp/Features/RulesPanel/Components/MatchRulesEditor.swift:MatchMapRulesEditor`
- `Sources/SpinLabApp/Features/RulesPanel/Sections/WorkflowSection.swift:workflowMatchRulesEditor` and measurement tag rules call site
- `Sources/SpinLabApp/Features/RulesPanel/Sections/SampleIdentificationSection.swift` batch/substrate call sites

### 4.f 风险 / 回滚路径

风险：unified editor 的 overloaded init 可能造成 call-site ambiguity。回滚路径：保持一个 `MatchRulesEditor` 名称，但使用明确 label `specs:` / `rules:`；不要恢复两个 public editor。

风险：切 op 时清空 output 可能丢掉用户刚从 unit-end 切回 equals 前的旧输出。可接受，因为 unit-end 下 output 已被定义为 `$MATCH`；如果要更友好，可以在 row-local `@State` 暂存上一次 editable output，但不作为 s1 必做。

## 6. 执行顺序

1. Domain/runtime：改 `FilenameRuleSet.ConditionDefinition`、compile/evaluate、RuleRef 最小兼容。
2. Bootstrap migration：新增 v5→v6，修 state skip gate，更新 bundled config。
3. Rules Panel draft：改 `MeasuringConditionFileDraft.ConditionDefinition`，移除旧 decode/encode 字段。
4. UI：合并 editor public API，替换 Batch / Substrate / Workflow / Condition 调用点，最后删除 Condition 双 binding。
5. Tests：先迁移与 round-trip，再 UI 契约，最后删旧 kind switch 断言。

---

## 7. 明确禁止

- 不保留 kind segmented control。
- 不保留“隐藏另一套规则但 raw storage 还在”的概念。
- 不在 runtime 或 Rules Panel draft 中长期兼容旧 `kind` / `unitPattern` / `tokenMap`。
- 不把 unit-suffix output 编码为 nil 或缺失。
- 不排序、不 rename、不 normalize 用户定义的 condition id / displayName / output value。
