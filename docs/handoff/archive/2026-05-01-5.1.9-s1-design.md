# 5.1.9 s1-design — Measuring Condition 单位标准化 handoff

Status: pending execution
Scope: design only. s1-exec 按本文执行；本文不含生产代码改动。

## 0. 总决策

5.1.9 在 5.1.8 已统一的 Condition `matches: [MapRule]` 上做增量扩展，不引入平行的 normalized condition 结构。每个 condition 增加一个集中语义对象 `ConditionStandardization`，承载 `standardUnit` 与 `precision`；每条 `MapRule` 增加可空 `transform` 字段，专门承载非标准单位到 standard unit 的表达式。运行时仍按 first-match wins 取同一条规则的 provenance，先按 `transform` 换算数值，再按 condition precision 清洗，最终只写 sidecar `conditionValues[id]` 的单个显示字符串。Rules Panel 保存后沿用 5.1.7 stale banner + `recomputeAllMeasurementSidecars`，不新增 recompute 管线。5.1.8 遗留的 NewRuleEntrySheet 死路径在同轮纯删除，并同步 Code Map 反登记。

## 1. v6 → v7 schema 迁移路径

### 1.a 决策 + 理由

**决策**：`measuring_condition.json` 从 version 6 升到 version 7。迁移继续落在 `RulesBootstrapper` 私有 JSON migrator，新增 `migrateMeasuringConditionV6ToV7IfNeeded(json:warnings:)`，并接在现有 v5→v6 之后。

理由：
- 这是 runtime-loaded config 的结构升级，启动迁移一次性完成，RuleLoader、Rules Panel draft、runtime 后续只面对 v7 canonical shape。
- 现有 `RulesBootstrapper` 已有 backup / tmp / verify decode / atomic replace / migration state / failure file 模板；5.1.9 必须复用，不写新的迁移工具。
- v7 是 additive schema：definition 新增 `standardization`，rule 新增可空 `transform`。旧 v6 文件迁移时默认不选择 standard unit、不设置 precision、不写 transform，行为等价当前现状。
- `.unitSuffix` 行的 `value = "$MATCH"` 约束保持不变；transform 不重载 `value`，避免破坏 5.1.8 已锁定的 output sentinel 语义。

迁移 shape：

```json
{
  "version": 7,
  "conditionDefinitions": [
    {
      "id": "current",
      "displayName": "Current",
      "standardization": {
        "standardUnit": null,
        "precision": null
      },
      "matches": [
        {
          "match": { "type": "unit-suffix", "value": "mA" },
          "value": "$MATCH",
          "transform": null
        }
      ]
    }
  ]
}
```

`standardization` 可以编码为 object，也可以在全 nil 时省略；s1-exec 选一种并保持 draft/runtime 一致。建议编码 object：字段稳定、UI round-trip 易测、未来扩展集中。

`transform` 建议 `String?`：nil 与空字符串运行时都表示“不换算”；保存时可把空白输入规范成 nil，避免 JSON 噪音。不得写 identity transform。

迁移状态：
- 将 `.migration_state.json.rules_schema_version` 升到 `7`。
- state skip gate 必须同时检查 state version 与 `measuring_condition.json.version`。即使 state >= 7，只要 measuring file version < 7，仍继续 measuring migration。
- 若 source measuring 已是 v7，migrator 原样返回，warnings 不新增。

### 1.b 受影响代码点

- `Sources/SpinLabApp/Import/Rules/RulesBootstrapper.swift:migrateRuntimeRulesIfNeeded`
  - 在 existing chain 后追加 v6→v7。
  - state skip gate 改为确认 measuring file version >= 7。
  - `writeMigrationState` 写 `rules_schema_version: 7`。
- `Sources/SpinLabApp/Import/Rules/RulesBootstrapper.swift`
  - 新增 `migrateMeasuringConditionV6ToV7IfNeeded(json:warnings:)`。
  - 迁移只处理 `measuring_condition.json`，不触碰 sample / workflow schema。
- `MigrationMeasuringConditionFile`
  - verify decode 目标改为能 decode v7 runtime `FilenameRuleSet.ConditionDefinition`。
- `Sources/SpinLabApp/config/measuring_condition.json`
  - 升到 `version: 7`，每个 definition 增加 `standardization` 默认空对象。
- `Sources/SpinLabApp/Features/RulesPanel/RulesManagementStore.swift`
  - draft model 与 encoder 输出 v7 shape。
- `Sources/SpinLabApp/Import/Rules/FilenameRuleSet.swift`
  - runtime model decode v7 shape；可兼容无 `standardization` 字段为 nil 以支持 migration verify 与手写 config。

### 1.c 风险 + 回滚

风险：`.migration_state.json` 已写到 7 但 runtime file 仍是 v6，导致启动跳过。执行层必须先修 skip gate，用 measuring file version 做二次确认。

风险：v7 additive 字段如果 Codable 设计不一致，Rules Panel 保存可能在 nil/object/omit 之间抖动。执行层必须用 round-trip 测试锁定字段稳定性。

风险：迁移 verify decode 失败。沿用现有策略：transform / encode / tmp write / verify decode 失败均不覆盖 runtime 文件；verify decode 失败写 `.migration_failed.json`，tmp 清理，原文件保持可用。

风险：atomic replace 失败。沿用现有 AppLogger error + backup 目录；用户可从 `.backup-<timestamp>/measuring_condition.json` 手动回滚。

## 2. 数据模型扩展

### 2.a Runtime model

`FilenameRuleSet.ConditionDefinition` 增加：

```swift
var standardization: ConditionStandardization?
```

新增 type 建议放在 `FilenameRuleSet.swift`，与 `ConditionDefinition` 同域：

```swift
struct ConditionStandardization: Codable, Hashable, Sendable {
    var standardUnit: String?
    var precision: Decimal?
}
```

理由：
- `standardUnit` / `precision` 是 condition 域语义，不属于 UI 控件，也不属于每条 rule。
- 集中 type 让 UI、evaluator、migration 都引用同一个 contract。
- 不需要新 protocol，不需要新 feature store。

`FilenameRuleSet.MapRule` 增加：

```swift
var transform: String?
```

Codable 行为：
- Decode 缺失字段为 nil。
- Encode 可省略 nil。
- 空白字符串在 draft 保存前归一为 nil；runtime 仍把空白视为 nil，防手写 JSON。

`ConditionDefinition` coding keys：
- `id`
- `displayName`
- `label` decode-only 兼容
- `standardization`
- `matches`

`ConditionStandardization.precision` 若 `Decimal` Codable 行为带来字符串/数字不稳定，执行层可选择 `String?` 存储 + computed Decimal parse，但必须仍集中在 `ConditionStandardization` 内，不散到 UI / evaluator。推荐优先验证 `Decimal` JSON round-trip；若不稳定，改为：

```swift
struct ConditionStandardization: Codable, Hashable, Sendable {
    var standardUnit: String?
    var precision: String?
}
```

并提供 `parsedPrecision` helper。

### 2.b Rules Panel draft model

`RulesManagementStore.MapRule` 同步增加 `transform: String?`。

`MeasuringConditionFileDraft.ConditionDefinition` 同步增加：

```swift
var standardization: ConditionStandardization
```

draft 的 `ConditionStandardization` 可以与 runtime 同名同 shape；若当前文件作用域导致类型不可共享，可在 draft 内定义同 shape 类型，但字段名、Codable 行为和 helper 语义必须一致。不要引入 `NormalizedCondition` / `ConditionUnitRule` 等平行结构。

初始化默认：
- `standardUnit = nil`
- `precision = nil`
- `matches` 原样

保存归一：
- `standardUnit` 若不在当前 `unit-suffix` / `regex` token options 中，UI 必须提示用户重选；不要静默清空后保存。
- `precision` 空白保存为 nil。
- `transform` 空白保存为 nil。
- `.equals` / `.contains` 行不消费 `transform`；保存时可保留 nil。若手写 JSON 在 equals/contains 上有 transform，UI 不展示，runtime 忽略。

### 2.c Config shape

Bundled `Sources/SpinLabApp/config/measuring_condition.json` 升 v7。默认不预选 standard unit，避免改变现有用户可见 sidecar 行为。

后续用户在 UI 中选择后，保存结果示例：

```json
{
  "id": "current",
  "displayName": "Current",
  "standardization": {
    "standardUnit": "mA",
    "precision": 0.1
  },
  "matches": [
    {
      "match": { "type": "unit-suffix", "value": "mA" },
      "value": "$MATCH"
    },
    {
      "match": { "type": "unit-suffix", "value": "A" },
      "value": "$MATCH",
      "transform": "*1000"
    }
  ]
}
```

## 3. 表达式引擎

### 3.a 文件落点与边界

新增独立 Swift 文件：

- `Sources/SpinLabApp/Import/Rules/ConditionTransformExpressionEvaluator.swift`

Code Map 登记到 `docs/architecture/inbox/ROUTING_PIPELINE.md`：

```markdown
- `Sources/SpinLabApp/Import/Rules/ConditionTransformExpressionEvaluator.swift` — evaluates numeric condition transform expressions
```

这是二级 shell：condition evaluator 只调用通用 API，不写运算符分支，不知道 `+` / `*` 细节。

Public/internal API：

```swift
struct ConditionTransformExpressionEvaluator {
    func evaluate(_ expression: String, value: Double) throws -> Double
}
```

错误类型：

```swift
enum ConditionTransformExpressionError: Error, Equatable {
    case empty
    case unexpectedCharacter(Character)
    case expectedNumber
    case trailingInput
    case divisionByZero
}
```

运行时可把 `.empty` 当“不换算”，或 evaluator 对空返回原值；推荐 evaluator 对空返回原值，condition evaluator 外层仍先 trim 判空以减少错误噪声。

### 3.b Parser / AST / evaluator

5.1.9 支持：
- 数字字面量：整数、小数、可带前导负号。
- 运算符：`+ - * /`。
- 优先级：`*` `/` 高于 `+` `-`。
- 无括号、无函数、无变量名。
- 表达式以当前匹配 token 的 numeric value 为隐式左值。

语义示例：
- `+273` 表示 `value + 273`
- `*0.001` 表示 `value * 0.001`
- `*1000+5` 表示 `(value * 1000) + 5`
- `/1000-2` 表示 `(value / 1000) - 2`

不要在 condition evaluator 中写：

```swift
if expression.hasPrefix("+") { ... }
```

推荐 parser 结构：

```swift
private enum Token { case number(Double), plus, minus, star, slash, end }
private enum Expr { case literal(Double), input, binary(BinaryOp, Expr, Expr) }
private enum BinaryOp { case add, subtract, multiply, divide }
```

为了表达“隐式左值”，parser 可在表达式前插入 `.input`，把 `*1000+5` 解析为 `(.input * 1000) + 5`。这比在 evaluator 中按字符串 prefix 分支更可维护。

### 3.c 错误处理策略

非法语法不应 crash，也不应阻断整个 filename parse。执行层采用：
- transform trim 后为空：不换算，原样保留。
- transform 非法：该 row 原样保留原始 token，产生 warning。
- division by zero：该 row 原样保留原始 token，产生 warning。
- warning 来源建议写入 `ExtraConditionEvaluationWithSources.warnings`，包含 condition id 与 rule index，不包含用户文件路径。

这样用户能通过现有 warning surface 看到规则错误，同时 sidecar 不写错误换算值。

### 3.d 测试矩阵

表达式引擎独立测试必须覆盖：
- `+273` with `27` → `300`
- `*0.001` with `2310` → `2.31`
- `*1000+5` with `2.31` → `2315`
- `/1000-2` with `5000` → `3`
- 空字符串 → 原值或上层判空不调用，按实现锁定
- 非法语法 `**2` throws
- trailing input `*1000abc` throws
- division by zero throws
- 优先级 `+2*3` with `10` → `16`

## 4. UI 改动清单

### 4.a condition 顶部控件落位

改 `MeasuringConditionSection.conditionDetail(idx:d:)`。Display Name 保持原位。`MatchRulesEditor` 的 Matches 标题行右侧增加：

- `Standard unit` picker
- `Precision` TextField
- 现有 `Case-insensitive` caption

落位仍在 `MatchRulesEditor` 标题 HStack 内，与 brief 要求同一行。不要写自定义视觉组件；使用现有 `LabeledContent` / `Picker` / `TextField` / `.roundedBorder` / AppSpacing / AppFontScale 模式。

推荐实现：扩展 `MatchRuleOutputBehavior`，让 MapRulesEditorBody 接受 condition 专用 header accessory，而不是在 `MeasuringConditionSection` 另写一套 row editor。

### 4.b MatchRulesEditor 扩展方式

保留共享壳，新增 output behavior case：

```swift
case conditionTransform(
    title: String,
    standardUnit: String?,
    unitOptions: [String],
    onInvalidStandardUnit: () -> Void
)
```

或等价的专用配置 struct。关键约束：
- 不影响 specs init。
- 不影响 Workflow measurementTagRules 的 `.editable`。
- 不影响 5.1.8 `.editableWithLockedOps` 行为。
- condition 调用点仍使用 `MatchRulesEditor`，不复制 `MatchRuleRowShell`。

如果 SwiftUI closure 存储使 `Equatable` 不方便，可把 `MatchRuleOutputBehavior` 的 Equatable 移除，前提是当前没有依赖 Equatable 的行为。不要为此新增 protocol。

### 4.c 第三框语义

行规则：
- `.equals` / `.contains`：第三框仍是 `Mapped to`，绑定 `MapRule.value`，可编辑。
- `.unitSuffix` / `.regex` 且 token == standardUnit：第三框灰显，显示 `$MATCH` 或 `identity`；存储保持 `value = "$MATCH"`，`transform = nil`。
- `.unitSuffix` / `.regex` 且 token != standardUnit：第三框可编辑，placeholder 用 `Transform`，绑定 `MapRule.transform`。
- standardUnit 未选择：所有 `.unitSuffix` / `.regex` 行第三框保持 5.1.8 现状，灰显 `$MATCH`，不展示 transform 编辑。

判断 token：
- `unit-suffix`：直接使用 `rule.match.value` trim 后的字符串。
- `regex`：本轮只把 `match.value` 作为用户填的 unit token 来源；如果 regex 是复杂 pattern，仍可列入 options 但不会解析 pattern。执行层若无法从匹配 token split 数字/单位，运行时原样保留。

### 4.d options 汇集逻辑

Standard unit picker options 只从当前 condition 的 `.unitSuffix` / `.regex` rows 汇集：
- trim 空白
- 排除空字符串
- 保持源顺序
- 去重
- 不包含 `.equals` / `.contains`
- 不大小写折叠，用户定义 token 原样保留

没有 options 时 picker disabled，standardUnit 保持 nil。

### 4.e 删除当前 standard unit 行

当用户删除 row 或把 row op/value 改到不再提供当前 `standardUnit`，UI 触发 alert：

文案功能语义：
- 标题：`Standard unit no longer exists`
- 信息：`Choose a standard unit from the current unit rows before saving.`
- 主按钮：`Choose Unit`

行为：
- 不静默保存失效 standardUnit。
- 可先允许 draft 处于 invalid 状态，但 Save 必须被挡住或弹同一提示。
- 用户选择新 standardUnit 后恢复保存。

### 4.f precision 输入

Precision TextField 是自由数字输入：
- 空白保存为 nil。
- 非数字或 <= 0 不参与清洗，并在 Save 时提示用户修正。不要运行时 silently discard UI 输入。
- 单位语义由当前 standardUnit 决定，UI 不额外拼接单位 label 到存储。

## 5. 评估器改造

### 5.a 主流程

改 `FilenameRuleSet.conditionEvaluationWithSources(from:)`，保持 first-match wins：

1. 按 `compiled.conditionRules[ruleID]` 顺序枚举 rule。
2. 找到第一个匹配 token。
3. 若 `rule.value != "$MATCH"`：输出 `rule.value`，忽略 transform。
4. 若 `$MATCH` 且 op 不是 `.unitSuffix` / `.regex`：输出 matched token。
5. 若 `$MATCH` 且 op 是 `.unitSuffix` / `.regex`：
   - split matched token 为 numeric + unit。
   - standardUnit 未选择：沿用现状，输出 normalize 后的原 unit token。
   - transform 为空：输出原 unit token，允许混合单位。
   - transform 非空：evaluate numeric，单位改为 standardUnit。
   - precision 有效且已换算到 standardUnit：`round(value / precision) * precision`。
   - format decimal + standardUnit。
6. 写 `RuleRef.conditionRule(id:ruleID, ruleIndex:ruleIndex)`。
7. break。

### 5.b 输出格式

保持当前 sidecar 单字符串合同：

- 无 transform：`"2.31A"` 或当前 normalize helper 输出格式；不要拆成 pair。
- 有 transform 到 standardUnit：`"2310mA"`。
- precision 清洗后：`"2310mA"` 或 `"2310.1mA"`，按现有 `formatDecimal` 去尾零。

现有 `normalizeUnitSuffixToken` 内按 hard-coded condition id（temperature / current / field）做 half-step / trimNoise / casing 归一化的整段路径，5.1.9 这一轮**整段删除**，**不保留** legacy fallback。standardUnit nil 时输出 raw matched token（不归一 casing、不 trim、不半步精度）；standardUnit 非 nil 时走新标准化路径。

理由：CLAUDE.md "Legacy Cleanup [HARD][must]: When replacing old behavior, remove superseded code paths in the same change"；Jack 已确认是唯一用户、可以接受历史 sidecar 在没设 standardUnit 的 condition 上从"隐式归一形态"变为"原 token 形态"（如 `80k` 不再被自动规整成 `80K`）。一次清干净，避免 hardcoding 长期残留。

### 5.c compiled rule 数据

`CompiledMapRule` 需要携带 `transform`。`CompiledConditionDefinition` 或等价结构需要携带 `ConditionStandardization`。

不要把 standardUnit、precision、unit options 编进每条 rule。它们属于 condition definition。

### 5.d regex 行

regex 行纳入 UI options 与 transform 逻辑，但运行时仍依赖 matched token 能被 `splitNumericUnitToken` 拆开。拆不开：
- 输出 matched token 原样。
- 产生 warning 可接受，但不必阻断 parse。

### 5.e provenance

继续使用 `RuleRef.conditionRule(id:ruleID, ruleIndex:ruleIndex)`。transform 与 precision 不改变 rule provenance，因为输出仍由同一条 condition rule 决定。

## 6. Recompute 联动

5.1.9 不新增 recompute 入口。

规则保存后流程保持：

1. Rules Panel save 写 runtime config。
2. `RuleLoader.shared` live 更新。
3. 5.1.7 stale banner 出现。
4. 用户点 Recompute。
5. AppState / LibraryStore 走现有 `recomputeAllMeasurementSidecars(rootURL:)`。
6. `recomputeSidecars` 内用 `FilenameRuleParser(ruleSet: loadResult.ruleSet)` 重新 parse。
7. `SidecarCompositionUseCase.composeSidecarV2` 写回 sidecar，`conditionValues` 变成新字符串。

执行层只需确保 parser 新语义被 recompute 调到；不要创建新的 backfill pipeline，不要让 Rules Panel save 自动改历史 sidecar。
