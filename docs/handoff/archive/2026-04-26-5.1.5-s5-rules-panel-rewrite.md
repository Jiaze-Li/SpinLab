## 3. Section 数据模型 + 编辑面（5 个）

每 section 都有：**Draft 类型 ↔ schema file** 一一对应；UI 列表内嵌主从布局；validation 在 save 时统一跑。

### 3.1 Section 1 — Import Filters
**Draft → file**：`ImportFiltersFileDraft` ↔ `import_filters.json`
**字段**：
```
version: Int
import: { supportedFileExtensions: [String], ignoredFileExtensions: [String] }
```
**UI**：两行可编辑 token list（chip 风格，逗号/换行分隔输入）— supported / ignored。
**Validation**：
- 后缀不能含空格 / 不能以 `.` 开头（Inbox 扫描层假设不带 `.`）
- supported 与 ignored 不能交叉（同一后缀不能两者都有）

### 3.2 Section 2 — Filename Tokenization
**Draft → file**：`FilenameTokenizationFileDraft` ↔ `filename_tokenization.json`
**字段**：
```
version: Int
tokenization: { separators: String, caseFold: String }
sources: [String]
channel: { aliases: [String: String] }
```
**UI**：
- separators：单行 TextField（可视化字符列表 + 直接输入）
- caseFold：Picker（preserve / upper / lower —— 现有取值仅 preserve，但 schema 允许其它，列出常见三个）
- sources：可重排列表（file / parent / grandparent，固定 3 项可勾选 + 拖拽排序）
- channel.aliases：key→value 编辑 list（add / delete / inline edit）

**Validation**：separators 非空；sources 至少含 1 项 + 仅允许白名单值（file / parent / grandparent）+ 去重；alias key/value 非空。
（Codex finding A4：补 sources 白名单 + 去重）

### 3.3 Section 3 — Sample Identification
**Draft → file**：`SampleIdentificationFileDraft` ↔ `sample_identification.json`
**字段**（嵌套保留 s3 决策的旧结构，UI 层做 row 化展开）：
```
version: Int
sampleId: { patterns: [String] }                       // 子区 A
substrate: {
  substrateTagRules: [MapRule],                        // 子区 B
  shared: SharedSubstrateRules                         // 子区 C（row-oriented 展开）
}
```
**UI**（detail 内分 3 子区，disclosure section）：
- 子区 A — Sample ID 正则模式：可编辑 list（`RegexField` 复用），add / delete / 上下移
- 子区 B — Substrate Tag Rules：复用 `MatchRuleEditor`（和原 SubstrateRulesSection 同形态）
- 子区 C — Substrate Materials（**ROADMAP 要求**："每行衬底材料后带显示成 X 字段"）：
  - row-oriented 展开：每行 = 一种衬底材料，列：`token`（如 `MGO`）/ `displayName`（如 `MgO`）/ `aliases`（指向该 token 的 alias 列表）/ `treatmentKeywords`（关联 treatment list）
  - 数据来源：把嵌套字典 `materialTokens` / `materialAliases` / `materialDisplayNames` / `treatmentKeywords` 在 ViewModel 层聚合为 `MaterialRow` 数组；保存时反向回填到嵌套结构
  - **行顺序策略（Codex finding A3 + §B.1 修订）**：以 `materialTokens` 数组为 row 主序列与主键来源；`materialDisplayNames` / `materialAliases` / `treatmentKeywords` 按 token 左连接挂载；不在 `materialTokens` 中的字典 key（orphan）**不静默丢弃**，UI 单独"未挂载 token"区显示并给修复入口（挂载 / 删除）。保存时按 `materialTokens` 顺序输出，仅孤儿条目兜底字母序 —— 不做全量字母序重排。
  - 另起 disclosure 子区：orientationTokens / orientationAliases / orientationPattern / originStandaloneTokens / originContainsTokens / tokenSeparators —— 这些不与材料 row 对齐，单独区域

**Validation**：
- patterns / orientationPattern：regex 合法性
- materialAliases 的 target 必须在 materialTokens 中
- orientationAliases 的 target 必须在 orientationTokens 中
- displayName key 必须是 materialTokens 成员（否则警告"未挂载到任何 token，将不生效"）

### 3.4 Section 4 — Workflow
**Draft → file**：`WorkflowFileDraft` ↔ `workflow.json`
**字段**：
```
version: Int
workflows: [{
  id: String,                              // 机器读，固定不改
  displayName: String,                     // 用户看，可改
  matchRules: [MatchSpec],                 // 文件名识别规则
  conditionFieldIDs: [String]              // 该 workflow 需要哪些 condition（引用 measuring_condition.conditionDefinitions[].id）
}]
measurementTagRules: [MapRule]             // 全局子标签清单（不分片）
```
**UI**：
- 上半区 — Workflows：list of workflow rows，每行展开（disclosure）后内嵌：
  - id（read-only TextField，灰底）
  - displayName（可编辑 TextField）
  - matchRules（复用 `MatchRuleEditor`）
  - conditionFieldIDs（multi-select chips，候选列表来源：当前 `measuring_condition.json` 的 `conditionDefinitions[].id`，需要 Store 层暴露 `availableConditionFieldIDs`）
  - 操作：复制本 workflow（新 row 用户自填 id）/ 删除
  - 顶部 "+ New workflow" 按钮 → 弹 prompt 输入 id（机器侧不再自动分配，对应 ROADMAP "WorkflowIDAllocator 退役" + "未来 UI 提供输入 ID 框"）
- 下半区 — Measurement Tag Rules：复用 `MatchRuleEditor`（和原 MeasurementTagRulesSection 同形态，但本期升级为可编辑而非只读）

**Validation**：
- workflow id 非空、唯一、无空白字符
- displayName 非空
- matchRules 至少 1 条
- conditionFieldIDs 中的每个 id 必须存在于 measuring_condition.json 的 conditionDefinitions（**跨 section 校验**：见 §4.3）
- measurementTagRules：MatchSpec 合法（regex 类型时 regex 合法）

### 3.5 Section 5 — Measuring Condition
**Draft → file**：`MeasuringConditionFileDraft` ↔ `measuring_condition.json`
**字段**：
```
version: Int
batch: { preferSampleId: Bool, fallbackPatterns: [String] }
conditions: {
  extraConditions: [String: String],         // condition id → unit_suffix regex
  tokenMapRules: [String: [MapRule]],        // condition id → token map rules
  displayLabels: [String: String]            // condition id → 用户可见 label override
}
conditionDefinitions: [{ id, label?, kind, binding }]  // kind: unit_suffix | token_map
```
**UI**（detail 内分 2 子区）：
- 子区 A — Batch 识别：preferSampleId Toggle + fallbackPatterns regex list
- 子区 B — Conditions：list of conditionDefinition rows，每行展开后内嵌：
  - id（read-only）
  - label（可编辑）
  - kind picker（unit_suffix / token_map）
  - 根据 kind 渲染：
    - `unit_suffix`：单个 RegexField，编辑 `extraConditions[id]`
    - `token_map`：MatchRuleEditor，编辑 `tokenMapRules[id]`
  - binding 字段不在 UI 暴露：Draft 类型也**不暴露 binding** — UI/Draft 用 `kind + payload` 语义模型，save 时由单点函数按 `kind` 生成 canonical binding 字符串（Codex §B.5 修订）。decode 仍容忍旧 binding（过渡兼容），但编码统一走生成逻辑，为 s7-1 删字段做准备。
  - **删除按钮交互（Codex finding A2 + §B.4 修订）**：删除按钮保留可用；点击后若该 condition 被任何 workflow 引用，弹强确认 sheet（列出受影响 workflow 数量 + 名称列表 + 默认按钮取消）；用户确认后删除并同步清掉 extraConditions / tokenMapRules 对应 key；保存 workflow 仍硬校验引用合法性（双层兜底）。
  - 顶部 "+ New condition" 按钮 → prompt 输入 id + 选 kind → 创建空记录

**Validation**：
- conditionDefinitions id 唯一
- kind ∈ { unit_suffix, token_map }
- unit_suffix kind 必须有 extraConditions[id]，且 regex 合法
- token_map kind 必须有 tokenMapRules[id]，且每条 MatchSpec 合法
- batch.fallbackPatterns regex 合法

## 4. 跨 section 基础设施

### 4.1 RulesManagementStore 重写要点
- 5 个 Draft 类型替换旧 4 个；新增 `importFiltersDraft` / `filenameTokenizationDraft` / `sampleIdentificationDraft` / `workflowDraft` / `measuringConditionDraft`
- 5 个 update 方法（每个 mark 对应 section dirty）
- 5 个 save 方法（每个跑对应 validation + persist）
- `loadSection(_:)` 走新 paths（importFiltersURL / filenameTokenizationURL / sampleIdentificationURL / workflowURL / measuringConditionURL）
- 删除旧 4 个 Draft 类型 + `MeasurementTagSummary`（measurementTag 升级为 workflow.json 子区，不再独立 section）
- 删除旧 paths 引用，但保留 `RulesConfigPaths` 中的旧 path properties（RulesMigration 还在用，s7 才删）
- `availableWorkflowIDs` 改名 `availableWorkflowIDs`（保留语义）+ 新增 `availableConditionFieldIDs`（来自 measuringConditionDraft.conditionDefinitions）—— 给 workflow section 的 conditionFieldIDs chip picker 用
- **availableConditionFieldIDs 外部刷新（Codex §C.4）**：在 `reloadAfterExternalChange(section: .measuringCondition)` 内同步刷新该缓存，避免外部改动后 picker 仍显示旧选项
- 跨 section 校验（workflow.conditionFieldIDs ↔ measuring_condition.conditionDefinitions.id）：在 saveWorkflow 时读 measuringConditionDraft 当前态校验；如果 measuring_condition section 当前 dirty，用 dirty 态而非磁盘态校验（保持窗口内一致性）

### 4.2 复用机制
- 关闭弹窗 / dirty 红点 / Save All / Discard All：现有 `RulesPanelView` 模式直接搬，case 数从 5 改 5（语义换）
- hash precondition + AtomicFileWriter + onRulesSaved + RuleLoader.reloadCached：现有 `persist()` 模板复用，逐 section 替换
- validation 错误展示：现有 `RulesPanelFieldError` + `RulesPanelSaveOutcome` 全保留

### 4.2.a Save All 顺序契约（Codex §C.1 + finding 4 修订）
**问题**：现有 `saveAllDirtySectionsAndCloseIfSuccessful()` 按 `dirtySections` (Set) 遍历，顺序不稳定 → workflow 与 measuringCondition 同时 dirty 时跨 section 一致性结果非确定。

**修订**：
- 单 section 保存：workflow 保存读取"内存中的 measuringConditionDraft（若 dirty）否则磁盘态"
- Save All：固定按 `RulesPanelSection.allCases` 顺序遍历 dirty section（即 importFilters → filenameTokenization → sampleIdentification → workflow → measuringCondition）；**注**：本次将 enum 顺序由 inbox 数据流定（measuringCondition 在最后）—— 因此 workflow 保存时 measuringCondition 仍在 dirty draft 中，依然命中"dirty 态校验"路径，无矛盾
- 任一 section 保存硬失败 → 自动切换聚焦到首个失败 section + 弹"已保存 X / 未保存 Y / 失败原因"汇总（Codex §C.3）

### 4.2.b 外部冲突 + Save All UX
- Save All 流程中遇 external conflict：定位首个失败 section + 自动切换聚焦
- 对话框列出 "已保存：[A, B] / 未保存：[C, D] / 失败：C 原因 = 外部冲突 / 操作 = Override / Reload / Cancel"

### 4.3 跨 section 一致性提示（运行时 vs 保存时）
- workflow.conditionFieldIDs 引用 measuring_condition.conditionDefinitions.id
- 删除 conditionDefinition 时不级联（用户操作太重）；改为 save measuringCondition 时检测引用悬挂，给软警告（不阻塞保存）：`"workflow.json 中 X 个 workflow 仍引用已删除的 condition 'foo'"`
- save workflow 时硬校验：每个 conditionFieldIDs 元素必须存在于当前 measuringConditionDraft（dirty 态）或磁盘态（无 dirty）
