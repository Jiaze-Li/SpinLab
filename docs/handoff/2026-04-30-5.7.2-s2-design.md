## 1. 背景与动机

s1 已建立「功能区 × 层」抽取模式（Inbox 4 层 5 文件，coverage 55/218），s2 复用模式抽 Library。

Library 当前文档分布：
- `docs/features.md` Library 段：Browse / Metadata Editing / Registry Sync / File Sync / Archive 五段
- `docs/architecture/INDEX.md` Library 段：first-read 表 + boundary rules（SP-006/007/008）+ tests
- `specs/01_PRODUCT_RULES.md`：少量涉及（apply 接收 / Clear Imports / audit log Library Root）
- `specs/02_DATA_RULES.md`（s1 已瘦身）：sidecar ownership 4 行已链接到 inbox/OUTPUT_CONTRACTS
- `specs/04_UI_RULES.md`：Library 视觉细节（detail section order）
- `specs/06_PROJECT_ARCHITECTURE.md`：Library 在项目架构里的位置

Library 与 Inbox 的关键差异是生命周期位置：Inbox 是 ingest 管线（pre-archive），Library 是 archive 后的浏览/编辑/搜索/同步/产物 inspection。**层名必须反映 Library 自身边界**，不能照搬 Inbox 的 4 层名。

## 2. 目标文件结构

```
docs/architecture/library/
  INDEX.md                     Library 子系统派发入口
  BROWSE_AND_SELECTION.md      浏览层：root view、column shell、selection、search/filter、detail section ordering
  ARCHIVE_STORAGE.md           存储层：drawer/index/settings、filesystem→app state sync、archive canonical、audit log
  SAMPLE_METADATA_EDITING.md   编辑层：sample edit transaction、registry diff/sync、display name 不被重命名
  SIDECAR_AND_CONDITIONS.md    契约层：sidecar 在 Library 的读取/展示、conditions/tags、Inbox/Workbench 共享边界
  ARTIFACTS_AND_PREVIEWS.md    产物层：_spinlab chart/metric artifacts、preview、path resolver、Workbench 写入边界
```

**6 份**（INDEX + 5 层）。

**为什么不照搬 Inbox 的 4 层**：Inbox 的核心动词是 parse/route/review/apply；Library 的核心动词是 browse/select/edit/sync/preview。Library 写成 pipeline 会掩盖它对 filesystem index、sample projection、sidecar display、artifact discovery 的长期维护边界。

**为什么 sidecar 独立成文件而非并入 Browse/Edit**：sidecar 在 archive 后被长期读取/展示，是独立的契约面（详见 §7 fix #1）。但**schema 表仍 owned by `inbox/OUTPUT_CONTRACTS.md`**，Library/SIDECAR 只描述读取行为 + 单向引用，避免双 canonical 漂移。

**为什么 sidecar 与 artifacts 不合并**：前者是 measurement file contract（被 Inbox/Library/Workbench 三方共享）；后者是 Workbench result artifact contract（核心是 `_spinlab` 路径、plot index、related charts）。变更风险和消费者不同。
