## 1. 范围

### 1.a UI 层

- **统一匹配编辑器**（替代当前 `UnifiedMatchRuleEditor`），双 view 共享 private row shell：
  - `MatchRulesEditor`：`@Binding rules: [MatchSpec]`，无输出列
  - `MatchMapRulesEditor`：`@Binding rules: [MapRule]`，含输出列
- 每行布局：`[Op Picker(allowedOps)] [Value TextField] [Output TextField (仅 Map)] [Delete]`
- 底部：`[Add]` 按钮
- 无嵌套展开层；所有匹配区标题统一为 **"Matches"**
- 调用点 6 处（详见 §6.c）

### 1.b 数据层

- 全仓 `MatchSpec` 收敛为单一扁平类型 `{type: Operation, value: String}`
- `MapRule` 改为 `{match: MatchSpec, value: String}`（`value` 是输出 token，沿用现役命名）
- `Operation` 枚举封闭 4 项：equals / contains / starts-with / unit-suffix
- 删除：`MatchScope` enum、6-op `MatchType` enum、`MatchSpec.scope`、`MatchSpec.matchValues / values`、`SubstrateEntry.Match.MatchType`（与新 Operation 合并）、`SampleIdRules.batchPrefixes / patterns` 字段、`ConditionDefinition.unitPattern / tokenMap` 字段、`compileSampleIdRegexes` / `firstRegexMatch` / `compileConditionDefinitions` 内部分支结构

### 1.c 引擎层

- 单一 `tokenMatches(text, MatchSpec)` 入口分发 4 op
- equals / contains 字面比对（保留 s11 lowercase 语义）
- starts-with / unit-suffix 在 compile 阶段合成 NSRegularExpression（CompiledMatchSpec.generatedRegex 缓存）
- substrate path 仍走独立 CompiledSubstrateEntry 但内部 op 来源换为新 Operation enum 子集

### 1.d 配置迁移

- workflow.json: v2 → v3
- sample_identification.json: v4 → v5
- measuring_condition.json: v3 → v4
- `.migration_state.json` rules_schema_version: 5 → 6
- 一次性原子迁移（atomic + .backup-<ts> 副本 + 幂等）；旧解码路径迁移完成后从生产代码删除（仅在 RulesBootstrapper 私有迁移函数内保留）

## 2. Unified Domain Model

### 2.a Operation enum

```swift
enum Operation: String, Codable, Hashable, Sendable, CaseIterable {
    case equals
    case contains
    case startsWith = "starts-with"
    case unitSuffix = "unit-suffix"
}
```

唯一运行时操作集；不含 regex / Any / unknown。Picker、迁移、引擎 dispatch、UI shell 全部使用同一 enum。

### 2.b MatchSpec（扁平）

```swift
struct MatchSpec: Codable, Hashable, Sendable {
    var type: Operation     // 字段名沿用现役 substrate v4 schema 的 "type"
    var value: String       // 单值（一条规则 = 一行 = 一个操作 + 一个单值）
}
```

字段名 `type` 沿用现役（substrate v4 已用 `{type: equals|contains, value}`）。Schema version bump 区分新旧 op alphabet。

JSON 形态：`{"type": "equals", "value": "AHE"}`

### 2.c MapRule（带输出，复用现役命名）

```swift
struct MapRule: Codable, Hashable, Sendable {
    var match: MatchSpec
    var value: String       // 输出 token；measurementTagRules 与 condition.token_map 共用
}
```

`value` 在 MatchSpec 与 MapRule 中分别承担"匹配输入"与"匹配输出"语义；不冲突（隶属不同结构）。

### 2.d SubstrateEntry 复用 MatchSpec

```swift
struct SubstrateEntry: Codable {
    var displayName: String
    var matches: [MatchSpec]    // 直接用 MatchSpec；UI 层限定 allowedOps = {equals, contains}
}
```

**删除** 原 `SubstrateEntry.Match` 内嵌类型与 `MatchType` 子枚举。Operation enum 是全仓全集；UI/迁移/校验决定每处接受的子集。

## 3. Schema Before / After

### 3.a workflow.json: v2 → v3

```json
// before (v2)
{ "version": 2,
  "workflows": [
    { "id":"MR", "displayName":"MR",
      "matchRules": [{"type":"equals", "matchValues":["MR"]}],
      "conditionFieldIDs": ["temperature","field"] }
  ],
  "measurementTagRules": [
    {"match": {"type":"equals", "matchValues":["AMR"]}, "value":"AMR"}
  ] }

// after (v3)
{ "version": 3,
  "workflows": [
    { "id":"MR", "displayName":"MR",
      "matchRules": [{"type":"equals", "value":"MR"}],
```

### 3.b sample_identification.json: v4 → v5

```json
// before (v4)
{ "version": 4,
  "sampleId": { "batchPrefixes": ["PN","PT","SL"] },
  "substrate": {
    "materials": [
      {"displayName":"STO", "matches":[{"type":"contains","value":"STO111"}]}
    ]
  } }

// after (v5)
{ "version": 5,
  "sampleId": {
    "matches": [
      {"type":"starts-with","value":"PN"},
      {"type":"starts-with","value":"PT"},
      {"type":"starts-with","value":"SL"}
    ]
  },
  "substrate": {
    "materials": [
      {"displayName":"STO", "matches":[{"type":"contains","value":"STO111"}]}
    ]
  } }
```

- `sampleId.batchPrefixes` / `sampleId.patterns` 字段从 schema 完全删除
- substrate.materials/treatments/orientations 内 `displayName` + `matches: [MatchSpec]` 不变（字段名稳）；allowedOps = {equals, contains}

### 3.c measuring_condition.json: v3 → v4

```json
// before (v3)
{ "version": 3,
  "conditionDefinitions": [
    { "id":"temperature", "displayName":"Temperature", "kind":"unit_suffix",
      "unitPattern":"^-?\\d+(?:\\.\\d+)?(?:K|k|C)$" },
    { "id":"device", "displayName":"Device", "kind":"token_map",
      "tokenMap": [{"match":{"type":"equals","matchValues":["wafer"]}, "value":"wafer"}] }
  ] }

// after (v4)
{ "version": 4,
  "conditionDefinitions": [
    { "id":"temperature", "displayName":"Temperature", "kind":"unit_suffix",
      "matches": [
        {"type":"unit-suffix","value":"K"},
        {"type":"unit-suffix","value":"k"},
        {"type":"unit-suffix","value":"C"}
      ] },
    { "id":"device", "displayName":"Device", "kind":"token_map",
      "matches": [{"match":{"type":"equals","value":"wafer"}, "value":"wafer"}] }
  ] }
```

**关键决断**：两类 kind 都用字段名 `matches`，但 element 类型按 kind 分支：
- `kind == "unit_suffix"` → `matches: [MatchSpec]`（无输出）
- `kind == "token_map"` → `matches: [MapRule]`（含输出）

字段名统一是为达成 ROADMAP 拍板要点 #3 的"标题统一为 Matches"+ AG5 的旧字样清理。Decode 时按 kind 分支选不同元素类型；详见 §4.c 与 §5.c。

`unitPattern` / `tokenMap` 两字段从 schema 完全删除。

### 3.d bootstrapper state version

`.migration_state.json.rules_schema_version`: 5 → 6。

## 4. 引擎改写策略

### 4.a Compiled 类型

```swift
struct CompiledMatchSpec {
    var spec: MatchSpec
    var generatedRegex: NSRegularExpression?    // 仅 startsWith / unitSuffix 持有
}

struct CompiledMapRule {
    var match: CompiledMatchSpec
    var value: String       // 输出 token
}
```

### 4.b 编译期：4 op 分发

```swift
private func compile(_ spec: MatchSpec, warnings: inout [String], label: String) -> CompiledMatchSpec {
    var compiled = CompiledMatchSpec(spec: spec, generatedRegex: nil)
    let trimmed = spec.value.trimmingCharacters(in: .whitespacesAndNewlines)

    switch spec.type {
    case .equals, .contains:
        if trimmed.isEmpty { warnings.append("\(label): empty value; rule never matches") }
        return compiled

    case .startsWith:
        guard !trimmed.isEmpty,
              trimmed.range(of: #"^[A-Za-z0-9_-]+$"#, options: .regularExpression) != nil else {
            warnings.append("\(label): invalid starts-with value '\(spec.value)' (non-alphanumeric); rule skipped at runtime")
            return compiled    // generatedRegex == nil → 永远不命中
        }
        let pattern = "^\(NSRegularExpression.escapedPattern(for: trimmed))\\d+$"
        compiled.generatedRegex = compileRegex(pattern, warnings: &warnings, label: label)

    case .unitSuffix:
        guard !trimmed.isEmpty else {
            warnings.append("\(label): empty unit-suffix value; rule never matches")
            return compiled
        }
        let pattern = "^-?\\d+(?:\\.\\d+)?(?:\(NSRegularExpression.escapedPattern(for: trimmed)))$"
        compiled.generatedRegex = compileRegex(pattern, warnings: &warnings, label: label)
    }

    return compiled
}
```

### 4.c 求值期：tokenMatches per-op

```swift
private func tokenMatches(text: String, compiled: CompiledMatchSpec) -> Bool {
    let value = compiled.spec.value.trimmingCharacters(in: .whitespacesAndNewlines)
    guard !value.isEmpty else { return false }

    switch compiled.spec.type {
    case .equals:
        return text.lowercased() == value.lowercased()
    case .contains:
        return text.lowercased().contains(value.lowercased())
    case .startsWith, .unitSuffix:
        guard let regex = compiled.generatedRegex else { return false }
        let range = NSRange(text.startIndex..<text.endIndex, in: text)
        return regex.firstMatch(in: text, options: [], range: range) != nil
    }
}
```

### 4.d MapRule 求值（first-match wins）

```swift
private func firstMatchValue(tokens: [String], rules: [CompiledMapRule]) -> String? {
    for rule in rules {
        if tokens.contains(where: { tokenMatches(text: $0, compiled: rule.match) }) {
            return rule.value
        }
    }
    return nil
}
```

**[HARD] source-order preserved**：迁移阶段从单条 legacy rule 展开多条新 rule 时**必须原位置展开**，不允许全局重排或合并跨规则。详见 §5.h。

### 4.e 特例代码消除

| 现函数 | s12 处置 |
|---|---|
| `compileSampleIdRegexes` | 整删除。`sampleId.matches: [MatchSpec]` 走统一 compile 路径 |
| `compileConditionDefinitions` 中 `case .unitSuffix` 分支（读 unitPattern + binding） | 删除分支结构。改为统一遍历 `definition.matches` 编译 |
| `compileConditionDefinitions` 中 `case .tokenMap` 分支 | 同上 |
| `firstRegexMatch` | 删除。unit-suffix 命中后引擎仍调 `normalizeUnitSuffixToken` 但路径合并入 firstMatchValue 的统一返回 |

合并后 `compiled.conditionUnitSuffixRegexes` 与 `compiled.conditionTokenMapRules` 两个字典合为单一：

```swift
struct CompiledRules {
    // ...
    var conditionRules: [String: [CompiledMapRule]]    // 替代 conditionUnitSuffixRegexes + conditionTokenMapRules
    // ...
}
```

unit_suffix 类 condition 的 matches 通过 wrap 一层"输出 = 命中 token"映射进 CompiledMapRule（具体策略见 §5.c）。

### 4.f Scope 退役

`MatchScope` enum 整删除（runtime 0 用，s11 已确认）。引擎里 `matches(rule:tokens:joined:)` 函数删除 scope dispatch；所有规则按 token 求值（不再有 joined 路径）。迁移阶段对 legacy `scope: joined` 仍然产 warning（详见 §5.f）。

## 5. 迁移算法

### 5.a 总流程（main entry）

`migrateRuntimeRulesIfNeeded()` 调整：

1. 读三份 runtime JSON（measuring / sample / workflow）
2. 检查 `.migration_state.json.rules_schema_version >= 6` 且三份文件都已是目标版本（measuring v4 / sample v5 / workflow v3）→ 写 source/target SHA 后跳过
3. 链式调用 v?→v?+1 迁移函数（保留所有更早 v1→v2 / v2→v3 链；新增三个 step）：
   - `migrateMeasuringConditionV3ToV4IfNeeded`
   - `migrateSampleIdentificationV4ToV5IfNeeded`
   - `migrateWorkflowV2ToV3IfNeeded`
4. `MigrationXXXFile` decode-verify struct 扩展到目标 schema
5. 写 `.migration-tmp-<ts>/` → backup `.backup-<ts>/` → atomic replace → 写 `.migration_state.json` rules_schema_version=6 + warnings
6. RulesBootstrapper 现有 scaffolding（atomic / verify-decode / backup / state file / 第二次启动跳过）一字不变复用

### 5.b 6 → 4 操作转换（workflow.matchRules + measurementTagRules + condition.tokenMap 通用）

| INPUT | OUTPUT |
|---|---|
| `{type:"equals", matchValues:["A"]}` | `[{type:"equals", value:"A"}]` |
| `{type:"contains", matchValues:["A"]}` | `[{type:"contains", value:"A"}]` |
| `{type:"equalsAny", matchValues:["A","B","C"]}` | 3 行：`equals A`, `equals B`, `equals C` |
| `{type:"containsAny", matchValues:["A","B"]}` | 2 行：`contains A`, `contains B` |
| `{type:"equalsOrContainsAny", matchValues:["A","B"]}` | **4 行严格顺序**：`equals A`, `equals B`, `contains A`, `contains B` |
| `{type:"regex", matchValues:[pattern]}` | drop + warning（详见 §5.e） |
| `{type:"equals", matchValues:[]}` | drop + warning "rule with empty matchValues dropped" |
| `{type:"equals", matchValues:["A","B"]}` (s11 单值约定下不应出现) | 拆 2 行 `equals A`, `equals B` + warning "type=equals with multiple matchValues treated as equalsAny" |

**Value 读取优先级**：`matchValues: [String]` > `values: [String]` > `value: String`（兼容旧多形态 decode）。trim whitespace；空值丢弃 + warning。

**equalsOrContainsAny 顺序锁死**：所有 equals 在前、所有 contains 在后；理由是贴近旧实现"先 equals 后 contains"的求值次序，AG4 行为对等回归靠这个顺序保住。

**MapRule expansion 重要约束**：当一条 legacy MapRule 展开为 N 条新 MapRule 时，**N 条都携带同一个 output value**（rule.value 原样复制）。

### 5.c sampleId.batchPrefixes → sampleId.matches

```
INPUT:  sampleId: {"batchPrefixes": ["PN","PT","SL"]}
OUTPUT: sampleId: {"matches": [
          {"type":"starts-with","value":"PN"},
          {"type":"starts-with","value":"PT"},
          {"type":"starts-with","value":"SL"}
        ]}
```

- 每个 prefix trim 后校验 `^[A-Za-z0-9_-]+$`，失败 → drop + warning `sample_identification: batch prefix '\(p)' is invalid and was skipped`
- 旧字段 `batchPrefixes` / `patterns` 从 schema 完全删除
- substrate matches 形态已是新 MatchSpec（字段名 `type` + `value`），仅顺道做 op 校验：发现非 {equals, contains} → drop + warning（防御性，现实数据上不会出现）

### 5.d measuring_condition v3 → v4

按 kind 分支：

**kind == "unit_suffix"**：
- 读旧 `unitPattern` 字符串
- 反解算法见 §5.f
- 反解结果作为 `matches: [MatchSpec]`（每条 op = `unit-suffix`）
- 删除 `unitPattern` 字段

**kind == "token_map"**：
- 读旧 `tokenMap: [{match: {type, matchValues}, value}]`
- 每条 legacy MapRule 按 §5.b 6→4 规则展开为 N 条新 MapRule
- 结果作为 `matches: [MapRule]`
- 删除 `tokenMap` 字段

**未知 kind**：fail migration（保留原文件，写 `.migration_failed.json` 含 reason；不发明语义）。

### 5.e regex 处置（彻底 drop）

旧 `{type:"regex", matchValues:[pattern]}` 整条丢弃，**不**尝试转换。warning 格式：

```
workflow: workflows[<id>].matchRules[<idx>] regex rule was removed during s12 migration: '<pattern>'
workflow: measurementTagRules[<idx>].match regex rule was removed during s12 migration: '<pattern>'
measuring_condition: conditionDefinitions[<id>].tokenMap[<idx>].match regex rule was removed during s12 migration: '<pattern>'
```

多个 pattern 用 `... '<first>' (+N more)` 简写。

### 5.f unitPattern 反解算法

**Canonical shape** （只接受这一种形态）：

```
^-?\d+(?:\.\d+)?(?:UNIT_ALTERNATION)$
```

具体步骤：
1. **Exact prefix match**: pattern startsWith literal `^-?\d+(?:\.\d+)?(?:`
2. **Exact suffix match**: pattern endsWith literal `)$`
3. 中间提取 = `UNIT_ALTERNATION` body
4. 按 literal `|` 切分得 candidates
5. 每个 candidate 校验：非空 + 不含 regex 元字符 `\()[]{}*+?.^$|`
6. 全部校验通过 → 输出 `[{type:"unit-suffix", value:c} for c in candidates]`，保持顺序，exact-duplicate 去重（保留首次）
7. 任一校验失败 → 见 §5.g

例：

```
"^-?\\d+(?:\\.\\d+)?(?:mA|A|uA)$"
→ [{"type":"unit-suffix","value":"mA"},
   {"type":"unit-suffix","value":"A"},
   {"type":"unit-suffix","value":"uA"}]
```

### 5.g 非典型 unitPattern 处置

**保留 condition + 写空 matches + warning**（不删除 condition）。

```json
// 反解失败的 condition
{ "id":"<id>", "displayName":"<name>", "kind":"unit_suffix", "matches": [] }
```

Warning：
```
measuring_condition: conditionDefinitions[<id>].unitPattern could not be converted to unit-suffix rows and was discarded: '<original_pattern>'
```

理由：删除 condition 会破坏 `workflow.conditionFieldIDs` 引用关系（workflow 数组里若含 "<id>" 但 measuring_condition 中已无该 id，会让 workflow 失效）。空 matches 在 UI 上可见可修复；backup 保留原 pattern 让用户/管理员可手工恢复。

### 5.h MapRule expansion 顺序约束（[HARD]）

每条 legacy rule 展开为 N 条新 rule 时：
- N 条**原位置**展开（即在原 rule 数组中插在原位置，先于后续 rules）
- 不允许跨规则全局重排
- 不允许跨规则合并去重
- N 条都携带同一 output value（适用于 measurementTagRules 与 condition.tokenMap）

**理由**：first-match 语义依赖 source order；展开后若重排会改变命中第几条，违反 AG4 行为对等。

### 5.i scope=joined 迁移 warning

旧 runtime 含 `scope: "joined"` → 静默改为 token-scoped（即不写 scope 字段）+ warning：

```
workflow: workflows[<id>].matchRules[<idx>] legacy scope 'joined' was removed; rule is now token-scoped
```

理由：runtime 0 用例（s11 已确认），但防御性 warning 不增成本。

### 5.j 幂等 + 原子 + .backup（复用现有 scaffolding）

- version-gated：目标版本直接返回（已是 v6 不重跑）
- verify-decode 通过前不替换 runtime 文件
- `.backup-<yyyymmdd-HHmmss>/` 含三份原 JSON
- `.migration_state.json` 写 source/target SHA + warnings + `rules_schema_version: 6`
- 第二次启动检测 v 已升即跳过（与 s9/s11 模式完全一致）

### 5.k 旧解码路径删除（迁移代码落地后一次性 burn）

s12-exec 完成迁移代码 + 测试通过后，**生产 runtime model** 一次性删：
- `MatchType` enum 中 `equalsAny / containsAny / equalsOrContainsAny / regex` 4 个 case
- `MatchScope` enum 整删除
- `MatchSpec.scope` / `.matchValues` / `.values` / 多形态 decode（替换为单 `value` decode）
- `compileSampleIdRegexes` 函数
- `firstRegexMatch` 函数
- `ConditionDefinition.unitPattern` / `tokenMap` 字段
- `compileConditionDefinitions` 中 kind 分支（合并为统一 matches 编译）
- `SampleIdRules.batchPrefixes` / `patterns` 字段
- `SubstrateEntry.Match` 内嵌类型 + `MatchType` 子枚举（合并到外层 `MatchSpec`）

更早 v1→v2 / v2→v3 / v3→v4 等所有迁移函数链**完整保留**（让有更老 runtime 的机器一次链式升到 v6）。Legacy decode 仅在 RulesBootstrapper 私有 migration 函数内存在；生产代码不可再引用。

## 6. UI 单壳契约

### 6.a Public API

```swift
struct MatchRulesEditor: View {
    @Binding var rules: [MatchSpec]
    let allowedOps: [Operation]      // 顺序就是 picker 顺序
    let defaultOp: Operation         // Add 按钮新增行的初始 op
}

struct MatchMapRulesEditor: View {
    @Binding var rules: [MapRule]
    let allowedOps: [Operation]
    let defaultOp: Operation
    let outputTitle: String          // 输出列 placeholder（默认 "Output"）
}
```

不用单一 view + `outputs?` 双数组同步（脆弱）；不用 enum case 区分（调用端拆分类型麻烦）。两个 view 共享 private row shell（详见 §6.b）。

### 6.b Private Row Shell

```swift
private struct MatchRuleRowShell<Trailing: View>: View {
    @Binding var operation: Operation
    @Binding var value: String
    let allowedOps: [Operation]
    let onDelete: () -> Void
    @ViewBuilder let trailing: () -> Trailing
}
```

行布局：
- 普通行（MatchRulesEditor 使用）：`[Op Picker(allowedOps)] [TextField(value)] [Delete]`
- 映射行（MatchMapRulesEditor 使用）：`[Op Picker(allowedOps)] [TextField(value)] [TextField(output)] [Delete]`
- 底部按钮：`[Add]`

视觉规则：
- 标题统一为 "Matches"（区块顶部）
- picker 全集顺序固定为 equals / contains / starts-with / unit-suffix；`allowedOps` 是子集过滤（保持原顺序）
- 单选项 picker 仍然显示（不退化为静态文本），保持单壳一致性
- 行内 control 顺序、sizing、间距严格一致

### 6.c 6 处调用映射

## 7. ConditionDefinition.kind 处置

**采纳 Option B**：保留 kind 作为操作白名单 + 输出语义标签。

```swift
struct ConditionDefinition: Codable {
    var id: String
    var displayName: String?
    var kind: ConditionDefinitionKind   // unit_suffix | token_map
    // 字段 binding / unitPattern / tokenMap 全删
    var matches: ConditionMatches       // 解码时按 kind 分支
}

enum ConditionMatches {
    case unitSuffix([MatchSpec])
    case tokenMap([MapRule])
}
```

decode：根据 kind 字段先决定，再 decode `matches` 数组到对应类型。encode 同理。

**为什么不删 kind**：

1. **builtIn 强约束**：ConditionFieldCatalog.builtInConditionIDs 把 temperature/current/field 钉为 unit_suffix、device 钉为 token_map。删 kind 会砸 builtin 概念，影响 fallback() / RuleLoader / RulesPanel 多处。
2. **mental model**：用户创建 condition 时，第一决断就是"这是数值带单位（温度/电流）vs 枚举映射（device→wafer）"。kind 在 UI 上一眼可见。
3. **operation whitelist 自然落点**：kind 直接驱动 allowedOps（kind=token_map → {equals, contains}；kind=unit_suffix → {unitSuffix}）。
4. **输出语义对齐**：token_map 命中后输出 rule.value；unit_suffix 命中后输出 normalizeUnitSuffixToken(token)。两种输出语义必须有 per-definition 字段区分 —— kind 即此字段。
5. **不增用户复杂度**：kind 选择器在 UI 已存在；s12 改的是录入界面（统一为 MatchesEditor），kind 选择留在 condition 顶层。

**统一性是行为级的**：s12 统一的是行 grammar（每行 = 一个操作 + 一个值）、操作集（4 种）、引擎 dispatch（per-op）、UI 壳（同一行布局）。**不抹掉** token mapping 与 unit extraction 的业务差异 —— 那个差异是真实的。

## 10. 风险 / 未决问题

### 10.a 风险

- **R1（unitPattern 反解失败的 condition 失效）**：非 canonical pattern 留下空 matches，runtime condition 不命中。处置：保留 condition + warning + .backup 留底，用户可在 UI 重建。可接受。
- **R2（runtime regex 合成开销）**：starts-with / unit-suffix 用 compile 阶段合成；compile 仅发生在 RulesBootstrapper / RuleLoader.reload 时，频次极低，性能影响可忽略。
- **R3（equalsOrContainsAny 拆 4 行散乱）**：用户改一行不会自动同步另 3 行。处置：迁移 warning 提示用户手动核对；ROADMAP 拍板已显式接受。
- **R4（test-only legacy evaluator 维护成本）**：AG4 验证依赖一个仅测试用的 6-op evaluator。处置：作为 V515RulesEngineRegressionTests 私有 helper；s12 完成后此 evaluator 仅用于历史回归对账，不进生产。
- **R5（substrate Match 类型合并影响范围）**：将 SubstrateEntry.Match 与新 MatchSpec 合并，substrate 解码 + compile 路径需同步动。处置：s12-exec 在 commit 1（domain + migration）一次性合并，substrate JSON schema 不变（字段名 `type` + `value` 已对齐），仅 Swift 类型层合并。

### 10.b 未决问题

- **U1（ConditionDefinition.matches 表达方式）**：Swift 上用 enum `ConditionMatches { case unitSuffix; case tokenMap }` 还是用 struct + optional `unitSuffixMatches: [MatchSpec]?` + `tokenMapMatches: [MapRule]?`？前者 type-safe 但 decode/encode 复杂；后者更直接但允许"两个字段同时填"的非法状态。**建议 enum**（强 type 边界；Codable 自定义 decoder/encoder 按 kind 分支）。s12-exec 自决。
- **U2（MatchSpec.value 是否需要 draft-only id）**：UI 上 ForEach 循环可能需要稳定 id；建议 draft layer 用 index-based ForEach 或外挂 UUID（不持久化到 JSON）。s12-exec 实施时按 SwiftUI 需求决定。
- **U3（migration warnings 输出位置）**：当前进 `.migration_state.json.warnings` 数组。是否需独立 log 文件？建议沿用现有方式（不增 surface）。
- **U4（Operation enum CaseIterable 顺序）**：picker 全集渲染顺序就是 `Operation.allCases` 顺序。declaration 顺序 = equals / contains / startsWith / unitSuffix；与 ROADMAP 列举顺序一致。
